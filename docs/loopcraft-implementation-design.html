Loopcraft / Implementation Design

Loopcraft Control Plane

A vendor-neutral system for declaring, scheduling, running, and monitoring background agent loops. One streamlined setup stands up the whole fleet on any vendor (Codex and Claude first), runs it cloud/always-on first, keeps its memory and produced artifacts in a git-backed store (separate from the source repo) mirrored to Linear, and surfaces everything — timelines, dependencies, approvals, and an inbox — in one web UI. This is the buildable companion to the Loopcraft field guide.

Portable by design A loop is a vendor-neutral package; thin adapters run it on Codex or Claude. No lock-in.
Declarative loops Each loop manifest encodes its dependencies, auth, env, execution locus, cadence, and upstream loops.
Cloud-first, observable Loops default to an always-on host; a web UI shows the fleet, a Gantt timeline, the dependency DAG, and the approval inbox.

TL;DR

Working name: Loopcraft Control Plane   Repo/package: loopcraft. CLI: loopctl. Host: an always-on Linux VM. First runtimes: Codex and Claude Code, with Cursor as a third adapter — the one that runs cross-provider sub-agents (e.g. GPT implementer + Opus reviewer) natively.

We propose a small control plane that turns the field guide’s loops into running infrastructure. A loop is declared once as a vendor-neutral manifest (logic + declared dependencies + execution locus + cadence). A runtime adapter translates that manifest into a headless Codex or Claude invocation, so swapping vendors is a one-line change. A scheduler deploys loops to an always-on host (cloud/VM first) as systemd units, ordered by their declared dependencies. State spans three stores in one git repo (loopcraft_memory, separate from the source repo): a git-versioned markdown/JSONL ledger (memory, the source of truth), a git-backed artifact store for the reports/diagrams/files loops produce (git-LFS for large blobs), and a Linear board (the human surface). A web UI renders the fleet, a Gantt-style run timeline, the loop-to-loop dependency DAG, and a unified inbox for approvals, reviews, and follow-ups.

Portability first Logic is vendor-neutral (a skill + I/O contract + tool list). Adapters for Codex and Claude map it to each CLI. Adding a vendor = adding an adapter, not rewriting loops.
Dependencies are explicit Every manifest declares its APIs, tool collections, auth, env vars, and upstream loops. The system validates them before a loop ever runs.

Trivial setup loopctl init → loopctl auth → loopctl apply. Three commands stand up the host, provision credentials, and deploy every loop.
Initial fleet (Section 11): a nightly code-sanitizing loop on nemotron-data-plane, the full W7 multi-source paper-discovery loop, an end-of-day contribution summarizer (via nv-tools), and a Slack triage/summarizer loop. These four exercise every part of the design.

Goals & Design Principles

These are the properties the system must have, in priority order. Everything downstream is in service of them.

1 · Vendor portability No lock-in to Claude, Codex, or any single product. The same loop runs on any supported runtime; the runtime is a configuration value, not a rewrite.
2 · Explicit dependencies A loop declares everything it needs to run: external APIs, tool/connector collections, authentication, environment variables, and other loops it consumes.
3 · Explicit execution Each loop states where it runs (local vs. VM/cloud) and on what cadence. Default is remote/always-on so loops are dependable, not laptop-bound.
4 · Trivial setup Standing up the whole fleet on a fresh host is a handful of commands. Adding a loop is dropping a manifest and re-applying.
5 · Monitorable A web UI visualizes the fleet, a timeline of runs, and the loop dependency graph — because no off-the-shelf dashboard does this across vendors.
6 · Human-in-the-loop The UI surfaces approval requests, an inbox, and a clear view of what needs review or follow-up. Irreversible actions are never autonomous.
7 · Durable, legible state Memory is a versioned markdown/JSONL ledger; produced reports/diagrams/files are persisted with provenance in an artifact store; both are mirrored to Linear for human action.
8 · Zero-blast-radius default Loops start read-only (observe) and only act within hard budgets. The control plane itself executes nothing irreversible.
9 · Explicit, earned promotion Every loop’s autonomy level (observe → propose → act) is a first-class, tracked property. A loop is only promoted after an evidence-based track record, and demoted automatically when it regresses. Promotion is a deliberate, auditable step — never a default.
Goal 9 in detail — the promotion lifecycle. Autonomy is not set-and-forget; it is a state machine the system manages and the operator approves:
  • observe (tier 0): read-only. The loop reports findings into the inbox; it changes nothing. Every loop starts here.
  • propose (tier 1): the loop drafts the action (a reply, an MR, a ticket) and parks it for one-click approval. Nothing happens until a human approves.
  • act (tier 2): the loop performs the action autonomously within hard budgets — reserved for reversible, low-stakes, in-house operations only.
Promotion rule: a loop graduates a tier only after N consecutive runs the operator would have approved unchanged (the accept-rate the harvester already tracks). The record lives in the loop’s state and the UI shows “X/N toward promotion.” Promotion is an explicit operator action (loopctl promote <loop> or a UI button), never automatic. Auto-demotion: if a promoted loop’s accept rate drops below threshold or it trips a budget/failure cap, it is automatically dropped a tier and flagged in the inbox. Irreversible actions (send/merge/spend) stay gated at propose forever, regardless of tier.
Non-goals (v0.1): building our own agent/LLM runtime (we wrap Codex/Claude), a hosted multi-tenant SaaS (this is single-operator), and auto-executing irreversible actions (sending external mail, spending money, force-pushing) without human approval.

Data & control flow

  1. You write or edit a manifest and run loopctl apply.
  2. The scheduler validates dependencies, then renders systemd units (and registers event/artifact triggers) on the host.
  3. On cadence (or trigger), a unit invokes the runtime adapter, which runs the loop headless on Codex or Claude inside an isolated worktree. Its tool calls route through the tool proxy, which auto-runs reads and queues gated calls for approval.
  4. The loop reads its declared inputs, writes memory to the state ledger (markdown/JSONL) and any produced artifacts (reports, diagrams, files) to the artifact store with provenance; actionable items are mirrored to Linear.
  5. The harvester records the run (status, cost, artifacts touched) and updates the inferred dependency graph.
  6. The web UI shows it all live; any approval the operator grants is routed back to the scheduler to release the gated action.
Key seam: loop logic never names a vendor. It references a skill, a tool list, and an I/O contract. The manifest’s runtime.vendor field (or a global default) selects the adapter at deploy time. That single indirection is the whole portability story.

The Loop Manifest

A loop is fully described by one declarative YAML file. It encodes the logic reference, the execution contract, and — per the requirements — every dependency explicitly. The control plane refuses to deploy a loop whose declared dependencies are unmet, so failures surface at apply time, not at 3am.

Annotated example

# loops/eod-summary.yaml
id: eod-work-summary
name: "End-of-day work summary"
description: "Scrape my contributions across Slack + GitLab and write a daily log."

runtime:
  vendor: codex            # codex | claude | cursor  (or omit -> global default)
  model: gpt-5.5-medium    # optional; adapter maps to vendor-appropriate flag
  reasoning_effort: medium

# optional: per-role models for a maker/checker (multi-model) loop.
# omit `roles` for a single-model loop (uses `runtime` + logic.skill above).
# each role binds an AGENT DEFINITION (behavior) + an execution binding (vendor+model).
roles:
  implementer:
    agent:  agents/implementer.md   # vendor-neutral agent def (instructions, tools)
    vendor: codex
    model:  gpt-5.5
  reviewer:
    agent:  agents/reviewer.md      # the checker's own instructions + readonly tools
    vendor: claude                  # cross-provider checker
    model:  opus
  # execution:
  #   intra-run  -> one harness spawns both as sub-agents (native on cursor)
  #   inter-stage-> control plane runs each as an ordered stage (any providers)

locus: vm                  # vm | cloud | local   (default: vm — always-on first)
cadence:
  type: cron               # cron | event | on-artifact
  at: "0 18 * * 1-5"       # 6pm on weekdays
tier: observe              # observe | propose | act
budget:
  max_turns: 20
  max_tokens: 400000
  max_runtime: 15m
  max_consecutive_failures: 2

# --- explicit dependencies: validated before the loop runs ---
depends_on:
  apis:   [slack, gitlab]
  tools:  [nv-tools]               # tool/connector collections
  auth:   [nv-tools, openai]       # credential bundles that must be present
  env:    [NVTOOLS_HOME]           # required environment variables
  loops:  [slack-triage]           # upstream loops this one consumes

# --- I/O contract: drives ordering + the dependency graph ---
inputs:
  - state/slack/triage-latest.md   # produced by slack-triage
outputs:
  - state/work-log/{{date}}.md
  - linear:project/Daily            # mirror a summary issue to Linear
artifacts:                          # produced files: persisted + versioned
  - path: summary.md   type: report   retention: keep

logic:
  skill: skills/eod-summary/SKILL.md   # vendor-neutral prompt/skill
  verify: "work-log file for today exists and lists >=1 contribution"

approval:
  required: false          # observe-tier: no approval needed

Roles are backed by agent definitions

A role is not just “a model” — it is a behavior bound to an execution. The behavior is an agent definition: a small, vendor-neutral spec (instructions, the tools it may touch, read-only vs. write, an optional stop/verify rubric) — the same shape as a SKILL.md, just scoped to one role. The execution binding (vendor + model) says which engine runs that behavior. Keeping the two separate is what lets you, say, point the reviewer behavior at Opus today and at a different model tomorrow without rewriting the reviewer’s instructions. 

# agents/reviewer.md  — a role's agent definition (vendor-neutral)
---
name: reviewer
description: "Adversarial code reviewer. Verifies the implementer's diff
              against the spec and tests; never edits code."
readonly: true                 # checker must not be able to 'fix' its own verdict
tools: [nv-tools.gitlab, repo-read]
verify: "every claimed issue cites a file:line; no false 'looks good'"
---
You are the checker, not the maker. Find what the implementer talked itself
into. Output: blockers, then nits, then an explicit PASS/FAIL.

At deploy time the adapter compiles each role’s agent definition into the chosen runtime’s native agent format — .codex/agents/*.toml, .claude/agents/*, or .cursor/agents/*.yaml — and attaches the role’s model. For an intra-run loop the harness spawns both as sub-agents in one process; for an inter-stage loop the control plane runs each agent definition as its own ordered adapter invocation, passing the diff through the memory ledger. Either way, the agent definition is the single source of truth for what a role does, and the vendor/model is a swappable binding on top of it.

Why this matters: separating behavior (agent def) from execution (vendor+model) keeps the maker/checker split portable and honest — the reviewer’s readonly: true and verify rubric travel with the role, not the model, so a checker can never quietly become a maker just because you swapped its engine.
Validation at apply: loopctl checks that every auth bundle is present, every env var is set, every tools collection is installed, every upstream loops id exists, and every roles.*.agent file resolves — and that inputs/outputs form a DAG (no cycles). A loop with an unmet dependency is reported, not deployed.

Vendor Portability — The Runtime Adapter

Portability lives in one narrow interface. Loop logic is expressed once as a skill (a SKILL.md with instructions), a declared tool list, and an I/O contract. A Runner adapter knows how to take that normalized invocation and execute it headless on a specific vendor, then return a normalized result (status, cost, logs, artifacts touched).

The Runner interface

class Runner(Protocol):
    vendor: str  # "codex" | "claude" | "cursor"

    def preflight(self, loop: LoopManifest) -> PreflightReport:
        """Check this vendor can satisfy the loop: tools mappable,
        auth present, model available."""

    def run(self, loop: LoopManifest, ctx: RunContext) -> RunResult:
        """Execute the loop headless in an isolated worktree.
        Returns status, token/cost usage, log path, artifacts touched."""

# RunContext: worktree path, env, resolved secrets, memory paths (ledger + artifacts)
# RunResult: status (done|stalled|failed|needs_approval), cost, logs, io

Codex and Claude are the first two adapters; Cursor is a third, called out because it is the one that runs cross-provider sub-agents natively (see Multi-model loops).

Portability caveats to handle in the adapter: capability gaps (a tool one vendor can’t do), cost/latency differences per model, and slightly different stop-condition semantics. preflight() exists precisely to fail fast when a loop names a capability the chosen vendor can’t satisfy — so you learn before deploy, and can pin that loop to the vendor that supports it.

Multi-model loops

A loop often wants different frontier models for different roles — e.g. a gpt-5.5 implementer with an opus reviewer/checker. There are two ways to get there, and the design supports both.

Mechanism A — intra-run (sub-agents inside one harness)

Each harness lets a sub-agent declare its own model, so the maker/checker split runs inside a single invocation. The catch is cross-provider (GPT and Opus in the same run):

  • Cursor — native. It brokers OpenAI/Anthropic/…, so a gpt-5.5 main agent can spawn a claude-opus reviewer sub-agent (.cursor/agents/ with a per-agent model). This is the cleanest fit for your exact example. (Caveat: per-sub-agent model selection on the CLI is plan-dependent — usage-based / Max Mode is reliable; prefer an explicit model id over inherit.)
  • Codex / Claude — same-provider only, natively. Sub-agents can use different models within the parent’s provider (e.g. gpt-5.5 + a cheaper gpt worker, or Opus + Sonnet). Cross-provider requires routing through a translating gateway (LiteLLM / OpenRouter).

Mechanism B — inter-stage (the control plane composes single-model runs)

Split the loop into stages and run each as its own adapter invocation with a different runtime/model, handing the artifact between them through the memory ledger: implement on codex / gpt-5.5, then review on claude / opus. This yields GPT + Opus across any providers with no gateway, using the same adapter seam and ordering machinery the rest of the design already has. It is the portable default.

Recommendation: support both. Use intra-run on Cursor when you want a single, tightly-coupled maker/checker loop with one process and shared context. Make inter-stage the portable default — it gives you a GPT maker + Opus checker on any mix of Codex/Claude/Cursor without depending on one harness brokering both providers, and every stage is independently observable, costed, and approvable.

Execution & Scheduling

Execution is remote/cloud-first: the default locus is the always-on Linux VM, so loops run whether or not your laptop is open (per the field guide’s Where Loops Run). local is the exception you opt into for interactive or private loops.

Scheduling & dependency ordering

loopctl apply renders each loop into a systemd .timer + .service pair (or registers an event/artifact trigger). Cron-style loops run on their schedule; on-artifact loops are woken by the supervisor when an upstream output changes — that is how W7→W8 style chains stay ordered without a central queue. 

# Generated by `loopctl apply` from loops/paper-discovery.yaml
# /etc/systemd/system/loop-paper-discovery.timer
[Timer]
OnCalendar=*-*-* 07:00:00
Persistent=true            # catch up if the VM was down at trigger time

# /etc/systemd/system/loop-paper-discovery.service
[Service]
WorkingDirectory=/srv/loopcraft/worktrees/paper-discovery
ExecStart=/usr/local/bin/loopctl run paper-discovery
# loopctl run -> selects adapter, resolves secrets, runs headless,
#                writes outputs to the memory tree, emits a run record
Ordering rule: the scheduler builds the DAG from inputs/outputs + depends_on.loops. A downstream loop either (a) runs on its own cadence and simply reads the latest upstream artifact, or (b) declares cadence.type: on-artifact to be woken the moment its input updates. Cycles are rejected at apply.

Persistent State

State has three stores, each tuned to what it holds: a state ledger (small, diffable memory), an artifact store (the reports, diagrams, and files loops produce), and a Linear board (the human surface). Code is excluded on purpose — it lives in its own repos — but everything else a loop emits is captured, versioned, and traceable back to the run that made it.

Logic and memory live in separate trees. The system’s source (the loopctl code, adapters, UI, loop manifests, and skills) lives in ~/workspace/loopcraft. The system’s memory (the ledger and the artifact store) lives in ~/workspace/loopcraft_memory. They are different repos with different lifecycles: source is reviewed, deployed, and shareable; memory is operator-specific data that grows over time and is synced across hosts. You can blow away and redeploy the source tree without touching a byte of memory — and back up or relocate memory without touching the code.

Tier 1 — the state ledger (canonical memory)

The memory tree (~/workspace/loopcraft_memory, cloned on the VM and synced to your laptop/Obsidian vault) holds every loop’s memory under ledger/. Each loop writes only to its own namespace. Because it is git, you get full history, diffs, blame, and rollback for free — the “memory spine” the field guide insists must live on disk. It keeps small, diffable text; large or binary outputs go to the artifact store (artifacts/, Tier 2) and are referenced from here.

Tier 2 — the artifact store (produced reports, diagrams & files)

Loops do not just update memory — they produce things: a code-quality report, a dependency diagram, a portfolio chart, a rendered PDF, an exported CSV. These are first-class, persisted outputs that live in the same loopcraft_memory git repo as the ledger, under artifacts/ — one repo, one history, one thing to back up. Small text artifacts (markdown, SVG, CSV) are committed directly; large or binary ones (PNG/PDF/parquet) are tracked by git-LFS in that same repo, with a small artifact manifest committed to git so the pointer, hash, and provenance are always versioned even when the bytes are LFS-backed. (An external object store is an optional offload for very large blobs, not a requirement.)

How artifacts are accounted for

  • Declared in the manifest. A loop lists what it emits under artifacts: (path or pattern + type + retention), so the system knows to capture and version them rather than letting them rot in a worktree.
  • Provenance on every artifact. Each gets a manifest.json: the producing loop + run id, a content hash, size/mime, and the hash of the inputs that produced it — so any report or diagram traces back to exactly the run and inputs that made it.
  • Immutable & addressable. Artifacts are write-once per run (dated/run-scoped paths, content-addressed). Re-runs produce new versions; nothing is overwritten, so history is intact.
  • Referenced, not duplicated. The ledger entry, the Linear issue, and the UI all link to the artifact by id; the bytes live once in the artifact store.
  • Retention policy. Per-artifact retention (e.g. keep reports forever, prune large intermediates after N days) keeps the repo (and its LFS store) from growing without bound.
# manifest excerpt: declaring produced artifacts
outputs:
  - state/code-sanitize/nemotron-data-plane/{{date}}.md   # ledger (text)
artifacts:
  - path: report.md            type: report    retention: keep
  - path: dep-graph.svg        type: diagram   retention: keep
  - path: "coverage-*.png"     type: image     retention: 30d

Tier 3 — the Linear board (human surface)

Loops that produce something a human must see, approve, or follow up on mirror it to a Linear project. Linear is reached through nv-tools (issues, projects, comments, relations) — the same connector layer the loops already use for Slack/GitLab/Jira, so there is no separate integration to build or authenticate. A finding becomes a Linear issue; its lifecycle (open → in review → approved/rejected → done) is the approval and review workflow. The markdown file remains canonical; the Linear issue links back to it and carries the human decision back.

Why three stores (in two repos): the ledger gives durable, diffable, agent-friendly memory; the artifact store — the artifacts/ dir of the same loopcraft_memory repo, with git-LFS keeping the diffable history lean — persists the actual reports and diagrams loops produce; Linear gives a familiar board, notifications, mobile access, and a natural approval state machine. Each item links to the others, so a Linear issue → its ledger finding → the exact report/diagram that backs it.
Conflict & identity policy: the ledger is authoritative for content, the artifact store for produced files (immutable per run), and Linear for human decisions (status/approval). The sync worker is idempotent and stores mappings (finding_id ↔ linear_issue_id, artifact_id ↔ blob) so re-runs update or version rather than duplicate.
One storage model — no per-loop side databases. Every loop reads and writes only through this shared model: small/seen/queue state → the ledger, produced files → the artifact store, run metadata/metrics → the single harvester SQLite (loopcraft_memory/loopcraft.db), human-actionable items → Linear. Loops must not stand up their own stores (the way the early prototypes kept separate state.sqlite3 files) — that fragments state, hides it from the control plane, and breaks versioning. A thin loopcraft.store API is the only sanctioned persistence path; ported code (e.g. the arXiv/X intel modules) is rewired onto it.

Fleet board

One row per loop across both vendors: status (running / idle / stalled / failed), vendor, locus, last run, next run, recent findings, rolling cost. The single screen the products don’t give you.

Each loop is a lane; each run is a bar positioned by start time and sized by duration, colored by outcome. You see at a glance the nightly cluster, overlaps, long-runners, and gaps where a scheduled loop silently stopped firing. Hovering a bar shows cost and a link to that run’s logs.

Dependency DAG (interaction graph)

Nodes are loops; edges are shared artifacts (loop B depends on loop A if B reads what A writes). The graph is inferred from the manifests’ inputs/outputs and confirmed by observed file accesses — you don’t draw it by hand. It highlights chains and flags a stalled upstream that is starving everything downstream.

Loop detail

Per loop: the rendered manifest, full run history with status/cost, the last log, and its position in the DAG. Crucially it also previews the produced artifacts — renders the markdown report, displays the generated diagram/chart/image, links the PDF or exported table — each tagged with the run that made it and a diff against the previous version. This is where you read what the loop actually did — the antidote to comprehension debt.

How it gets the data: the harvester watches ~/.codex/, ~/.claude/, and the memory tree (run records + artifact mtimes), normalizes runs across vendors into SQLite, and serves them over a REST/WebSocket API. The UI is a thin client over that.

Inbox, Approvals & Review

Most loops in the fleet produce things a human must act on: a fix to approve, a reply to send, a finding to triage. The control plane funnels all of these into one inbox — the operational core of the human-in-the-loop requirement (field guide rollout + monitoring).

What lands in the inbox

Approval requests From propose/act loops: “send this reply,” “open this MR,” “file this ticket.” One-click approve/reject; approval releases the gated action via the scheduler.
Review items Outputs worth your eyes even if no action is gated — the code-sanitize findings, the daily summary, anything the loop flagged as high-signal.
Follow-ups Commitments and open threads the loops detected (“you said you’d reply to X”), so nothing slips.
Alerts Operational problems the loop can’t fix itself: a failed run, a stalled chain, an exhausted budget, a missing credential.

The approval mechanism

  1. A propose/act loop finishes its work but stops before the irreversible step, writing a request to inbox/ with status needs_approval and the exact action it wants to take.
  2. The sync worker mirrors it to Linear and the UI surfaces it in the inbox.
  3. You approve or reject (in the UI or in Linear). The decision is written back to the file and the Linear issue.
  4. On approval, the scheduler runs the loop’s release step (a bounded follow-up invocation) that performs the now-approved action and records the result.
Inbox [ 3 need approval ] ───────────────────────────────────────────────────────────────────────── ⚑ NEEDS APPROVAL slack-triage Reply draft to @alice (#nemotron-data) [ View ] [ Approve & send ] [ Reject ] ⚑ NEEDS APPROVAL code-sanitize Open MR: fix null-deref in loader.py [ View diff ] [ Approve & open ] [ Reject ] ◆ REVIEW eod-work-summary Today: 4 MRs, 11 Slack threads, 2 reviews ◷ FOLLOW-UP slack-triage You owe @bob an answer on RFC (2d old) ✕ ALERT code-sanitize Run failed: gitlab auth expired ─────────────────────────────────────────────────────────────────────────
Two granularities of approval. The mechanism above gates the loop’s anticipated action at the loop boundary — the author knows the irreversible step is coming and structures the loop to stop there. But an agent may decide mid-run that it needs a gated tool the author didn’t anticipate. For that we gate at the tool-call level too.

Tool-call approvals — the guarded tool proxy

In headless/unattended mode on the VM there is no interactive permission prompt — a tool call either runs or it doesn’t. So we move the approval boundary down to the tool layer: every tool call routes through a guarded proxy (an MCP shim / nv-tools wrapper) that holds a per-loop policy of which tools require approval. This makes approval per-call, mid-run, and vendor-independent — the agent never executes a gated action itself, in any tier, even if it “decides” to.

  1. The agent calls a tool. The proxy checks the policy.
  2. Not gated (e.g. a read) → executes normally and returns the result.
  3. Gated (e.g. a WRITE / external send) → the proxy does not execute. It records the intended call (tool + args) to inbox/ as a pending approval and returns a structured queued: pending-approval result, so the agent logs what it wanted and exits gracefully instead of hanging.
  4. You approve/reject in the UI or Linear. On approval a separate executor performs the call, records the result, and (optionally) feeds it back on the loop’s next run.
Why a proxy, not the vendor’s prompt: it works headless on the VM, it is identical across Codex and Claude (preserving portability), and it sits on top of nv-tools’s existing READ/WRITE safety model — the proxy simply refuses to pass --write for a gated tool until the call is approved. Reads stay friction-free; mutations are caught by construction.

Declaring the policy in the manifest

Each loop declares which tools are gated; sane global defaults mean you rarely have to (any WRITE / external send is gated unless explicitly opened).

# in a loop manifest
depends_on:
  tools:
    - name: nv-tools.slack.search   approval: auto       # read-only: runs freely
    - name: nv-tools.slack.send     approval: required   # gated: queue + approve
    - name: nv-tools.gitlab.mr      approval: required
policy:
  default: { writes: required, reads: auto }   # any WRITE gated unless overridden
Tool call (mid-run) │ ▼ [guarded proxy] ── policy? ──▶ auto ──▶ execute ──▶ result to agent │ └─▶ required ─▶ inbox: "pending approval" (tool + args) │ agent gets {queued} and exits gracefully ▼ you approve ─▶ [executor] runs it ─▶ result recorded
Two paths, composed. The loop-boundary release step stays the clean path for anticipated actions (the agent finished a plan you approve in one click). The guarded proxy is the safety net for unanticipated gated calls mid-run. For locus: local loops you may additionally allow the vendor’s interactive permission prompt; the proxy is what makes it work on the always-on VM.
Hard rule: sending external messages, opening MRs/PRs, spending money, and any other irreversible action are always gated — at the loop boundary or by the proxy — regardless of tier. act tier only auto-executes reversible, low-stakes, in-house operations (e.g. writing a state file, filing an internal draft ticket).

Trivial Setup

Standing up the whole system on a fresh always-on host is a one-time dependency install (step 0) plus three commands. Adding a loop is dropping a manifest and re-applying. This is the “setup should be trivial” requirement made concrete.

Bootstrap

# 0 · install loopctl + ALL dependencies on a clean host (idempotent).
#     This is the only step that needs system-level installs.
curl -fsSL https://<loopcraft>/install.sh | bash      # installs the loopctl CLI
loopctl deps install --runtimes codex,claude,cursor
#   installs + version-checks everything the fleet needs:
#     • runtimes:  codex CLI, claude code, cursor-agent (Cursor CLI)
#     • connector: nv-tools  (Slack/GitLab/Jira/Linear/...)
#     • storage:   git + git-lfs  (memory tree, LFS artifacts)
#     • runtime:   python, node  (loopctl + the web UI)
#     • host:      systemd present (timers); MCP shims for the tool proxy
loopctl deps check                                    # report any gaps, no installs

# 1 · bootstrap the host. Clones SOURCE to ~/workspace/loopcraft and
#     inits MEMORY at ~/workspace/loopcraft_memory (paths are configurable).
loopctl init --host vm --runtimes codex,claude,cursor \
        --source ~/workspace/loopcraft \
        --memory ~/workspace/loopcraft_memory

# 2 · provision all credentials in one guided flow
loopctl auth          # walks through nv-tools, openai, anthropic, slack, gitlab, linear

# 3 · deploy every loop in loops/ (validates deps, renders units, starts timers)
loopctl apply ./loops

# that's it — the fleet is live and the UI is up
loopctl ui            # prints the dashboard URL
What step 0 covers: it installs the per-vendor runtimes you ask for (so the adapters have a CLI to call), the shared nv-tools connector layer, git-lfs for the artifact store, and the python/node the control plane and UI need. loopctl deps check is the same probe preflight runs before any loop — so a missing runtime is reported at install time, not at 3am. Re-running step 0 is safe (idempotent) and is how you add a runtime later (e.g. loopctl deps install --runtimes claude).

The source–memory wiring lives in one config file in the source tree:

# ~/workspace/loopcraft/loopcraft.toml
default_vendor = "codex"
host           = "vm"
memory_path    = "~/workspace/loopcraft_memory"   # ledger/ + artifacts/ + loopcraft.db
# artifact_store = "s3://..."  # optional: large/binary blobs offloaded here

Everyday operations

loopctl add slack-triage      # scaffold a new manifest + skill from a template
loopctl run eod-work-summary  # run one loop now (ad hoc), stream its output
loopctl status                # fleet status in the terminal
loopctl fleet                 # all loops in one table: schedule, last run, install state
loopctl logs paper-discovery  # tail a loop's last run
loopctl reindex               # rebuild loopcraft.db from logs + ledger (DB is derived)
loopctl vendor set claude     # flip the global default runtime (portability!)
loopctl promote slack-triage  # graduate a tier (observe->propose->act) once earned
loopctl demote  slack-triage  # drop a tier manually (auto-demotion also happens)
loopctl apply ./loops         # re-deploy after any change
loopctl remove slack-triage   # undeploy one loop (disable + delete its units)

Repo layout — logic and memory are separate trees

~/workspace/loopcraft/         # SOURCE (logic): reviewed, deployable, shareable
  loopctl/                     # the CLI + scheduler + adapters + harvester + tool proxy
    adapters/{codex,claude}.py
  ui/                          # React dashboard
  loops/                       # YOUR manifests (one yaml per loop)
    slack-triage.yaml
    paper-discovery.yaml
    eod-summary.yaml
    build-review-ship.yaml
  skills/                      # vendor-neutral SKILL.md per loop
    slack-triage/SKILL.md
    paper-discovery/SKILL.md
    ...
  agents/                      # vendor-neutral agent defs for roles (maker/checker)
    implementer.md
    reviewer.md
  loopcraft.toml               # global config: default vendor, host, memory path

~/workspace/loopcraft_memory/  # MEMORY: operator-specific data, synced + backed up
  ledger/                      # versioned state (markdown/JSONL) — the memory spine
  artifacts/                   # produced reports/diagrams/files (git-LFS, same repo)
  loopcraft.db                 # SQLite run history/metrics (harvester)
Why split the trees: the source repo is what you review, deploy, and could open-source; the memory repo is your private, ever-growing data. Re-clone or upgrade ~/workspace/loopcraft without risking memory; back up, snapshot, or move ~/workspace/loopcraft_memory independently. loopcraft.toml simply points the source at the memory path, so the two are wired together at runtime but versioned apart.
Portability in one command: because logic is vendor-neutral, loopctl vendor set claude (or a per-loop runtime.vendor) re-points the entire fleet at a different runtime. The same loops, the same state, a different engine.

Initial Loops

Four loops to build first, in build order — lowest-risk observe loops first, the multi-model build/ship loop last. Together they exercise every part of the design: multiple vendors, all three tiers, file + Linear state, the dependency graph, the approval inbox, and a cross-provider maker/checker. All default to locus: vm.

How they connect

[L1 slack-triage] ─▶ state/slack/triage-latest.md ──┐ ▼ [L2 paper-discovery]─▶ research/discovery-queue.jsonl [L3 eod-summary] ─▶ work-log/ + Linear (feeds future W8/W9) [L4 build-review-ship] task (inbox/backlog) ─▶ branch + MR draft ─▶ inbox (approval) implementer = codex/gpt-5.5 reviewer = claude/opus

L1 — Slack triage & summarizer

Cadence: 3×/day (09:00, 13:00, 17:00). Tier: observe→propose. Deps: nv-tools slack. Outputs: state/slack/triage-latest.md + inbox items.

Scans everything aimed at you — @mentions, DMs, group DMs, and a configured list of high-signal channels — and produces a categorized digest: action required / review-FYI / informational, leading with what needs a reply and ending with a prioritized checklist. At propose tier it drafts replies to the easy ones and parks them in the inbox (sending is always approval-gated). Pure observe to start — the lowest-risk loop, built first. 

$slack-triage
Scope: @mentions, DMs, group DMs, channels in skills/slack-triage/channels.txt.
Window: since last run (cursor in state/slack/seen.json).
- categorize: ACTION / REVIEW / FYI ; dedup threads
- write state/slack/triage-latest.md (lead with action items + checklist)
- surface ACTION items to inbox; (propose) draft replies, approval-gated

L2 — Multi-source paper discovery (full W7)

Cadence: daily 07:00. Tier: observe. Deps: arXiv API, X/Twitter lists, newsletter inbox (nv-tools outlook/gmail), RSS, Glean. Outputs: research/discovery-queue.jsonl, research/seen.json.

The full W7 loop, not just arXiv. Fans out across arXiv (cs.CL/LG/AI, filtered to post-training/RLHF/RLVR/distillation/reward-modeling/evals/agentic), curated X lists, subscribed newsletters, RSS, and Glean; normalizes every hit to a common record; dedups across sources; scores against research/themes.md; and appends keepers to one queue with a one-line “why.” It is the funnel that feeds the future W8/W9 reading/experiment loops.

Reuse existing prototype code. Two of L2’s sources are already built in the ~/workspace/loopcraft source tree and can be lifted in directly:
  • loopcraft.arxiv_intel — an abstract-first arXiv workflow with client, ranking (relevance scoring), and digest; automation-ready via scripts/daily_arxiv_intel.sh.
  • loopcraft.x_intel — an X/Twitter workflow on the official X API with client, ranking, digest, and follow_discovery (surfaces new accounts to follow); CLI verbs snapshot-following / run / discover-follows.
  • Bundled skills arxiv-intelligence-reporting and x-intelligence-reporting already encode the reporting behavior.
So the arXiv and X sources, their relevance ranking, and digest logic already exist. What L2 adds on top: the remaining sources (newsletters via nv-tools Outlook/Gmail, RSS, Glean), and a thin normalizer that merges all sources into the single research/discovery-queue.jsonl (+ seen.json) and scores against research/themes.md — reusing the existing ranking and digest code as the starting point.
Migration: drop the per-tool SQLite stores. The prototypes each keep their own state.sqlite3 (var/arxiv_intel/, var/x_intel/). Those are retired in favor of the unified storage model: dedup/seen and queue state move into the ledger (research/seen.json, research/discovery-queue.jsonl) in the memory tree, and run metadata into the single harvester DB (loopcraft_memory/loopcraft.db). The store modules are reimplemented against that shared layer — no loop keeps its own side database, so state stays versioned, diffable, and visible to the control plane. 
$paper-discover

  - normalize to {title, authors, url, source, date, abstract, surfaced_by}

L3 — End-of-day work summarizer

Cadence: daily 18:00 (weekdays). Tier: observe→propose. Deps: nv-tools (slack, gitlab, jira, linear, calendar); consumes slack-triage (L1). Outputs: work-log/{{date}}.md + Linear Daily.

Uses nv-tools to scrape the day’s contributions across Slack (your messages/threads), GitLab (commits, MRs opened/reviewed), Jira, and Linear (issues you completed or moved — including those closed by other loops, like L4’s shipped MRs), plus the L1 Slack triage output, into a single dated work-log entry. This rolls forward all year so focal self-assessment becomes a query. At propose tier it also drafts a standup blurb for approval. First loop with an upstream dependency. 

$eod-summary

- collect my Slack messages/threads, GitLab commits + MRs (authored & reviewed)
- tally completed work: Jira moves + Linear issues closed/advanced today
- fold in state/slack/triage-latest.md   # from L1
- write state/work-log/{{date}}.md grouped by project, with links as evidence
- mirror a concise summary to Linear:Daily

L4 — Build → Review → Iterate → Ship (multi-model)

Cadence: on-artifact (a task lands in the backlog) or manual. Tier: propose. Roles: implementer = codex / gpt-5.5, reviewer = claude / opus. Deps: gitlab auth, repo checkout, test runner, both runtimes (codex + claude), the two agent defs. Outputs: a per-ticket feature branch + an MR draft parked in the inbox + a build-log artifact.

The most complex loop, built last — and the canonical cross-provider maker/checker (the multi-model pattern made real). It always cuts a fresh feature branch per ticket (e.g. loopcraft/<ticket-id>-<slug>) off the latest main and works only there — never on main directly. Given a scoped task, the implementer (Codex / GPT-5.5) writes the change on that branch in an isolated worktree and gets the tests green; then the reviewer (Claude / Opus, read-only) grades the diff against the spec and tests. If the reviewer returns blockers, the implementer iterates; the loop repeats until both the reviewer passes and the gates are green, or the budget is hit. On success it ships a draft MR (feature branch → main) into the approval inbox — it never pushes to main or merges on its own. Maker and checker are deliberately different providers so the reviewer isn’t grading its own homework.

Execution is inter-stage (implement on Codex, review on Claude, iterating via the memory ledger) so it works cross-provider with no gateway; on Cursor it can also run intra-run with both as sub-agents in one process. 

$build-review-ship
Input: a scoped task/ticket (from inbox/backlog) with an explicit acceptance check.
Repo: <target>. Fresh worktree off origin/main.
BRANCH: always create a new feature branch  loopcraft/<ticket-id>-<slug>
        from latest origin/main. NEVER commit on main.

LOOP until reviewer=PASS and gates green, or max_iterations:
  1. IMPLEMENTER (codex/gpt-5.5, agents/implementer.md):
       commit the smallest change that satisfies the task to the feature branch;
       run lint+tests
  2. REVIEWER (claude/opus, agents/reviewer.md, readonly):
       grade the diff vs the spec + tests; emit blockers/nits + PASS|FAIL
  3. if FAIL -> feed blockers back to the implementer; iterate
SHIP: open a DRAFT MR (feature branch -> main), attach build log + reviewer verdict,
      request approval in inbox.
Tier=propose: never push to main or merge without approval.
Stop condition: “reviewer verdict = PASS and pytest/lint exit 0,” bounded by max_iterations — a verifiable contract, not “looks done.” The reviewer’s readonly: true (from its agent def) guarantees it can flag but never “fix” its way to a green verdict.
Coverage & build order: L1 exercises high-frequency cadence + propose-tier drafts; L2 exercises multi-connector fan-out + dedup state; L3 exercises cross-tool scraping + an upstream loop dependency; L4 exercises the full multi-model maker/checker (two providers), iterate-to-green stop condition, MR-drafting, and approval gating. Build in order: L1 → L2 (pure observe, lowest risk), then L3 (depends on L1), then L4 last (the only one that writes code and the only multi-model loop).

Coverage of the Six Loop Primitives

The field guide defines a loop as five primitives plus a memory: automations, worktrees, skills, connectors, sub-agents, and state. A useful test of this design is whether it actually delivers all six. The short version: it implements every one — mostly by composing capabilities the vendors already ship and adding the cross-cutting layer (manifest, scheduler, state, UI) that turns them into a managed fleet.

PrimitiveField-guide jobHow this design delivers itCoverage
Automations (heartbeat) Trigger the loop on a cadence without you. The scheduler renders each manifest’s cadence into systemd timers; a supervisor handles event/on-artifact triggers; the adapter wraps a /goal-style stop condition. Strong
Worktrees (isolation) Parallel agents that can’t collide. Every run executes in an isolated worktree via the adapter (Codex built-in; Claude git worktree); RunContext hands the loop its own checkout. Strong
Skills (codified knowledge) Project knowledge the agent reads every run. logic.skill points at a vendor-neutral SKILL.md in skills/; loopctl add scaffolds one; it’s versioned in git and identical across vendors. Strong
Connectors (real tools) Act inside your actual environment. nv-tools + MCP as the unified connector layer, declared per loop in depends_on.tools/apis/auth and validated pre-deploy. Same layer serves Linear. Strong
Sub-agents (maker vs checker) A separate agent grades the work. Delegated to the runtime (.codex/agents / .claude/agents); the L4 build/ship loop uses a cross-provider implementer + reviewer. The harvester surfaces sub-agent trees from vendor logs. Strong, delegated
State / memory (the spine) Persist what’s done outside the conversation. The most developed part: a three-store model (ledger + artifact store + Linear), versioned, with provenance and an explicit inputs/outputs contract. Strong

The one nuance: sub-agents are delegated

The only primitive the control plane does not own is sub-agents. By design, the plane treats a loop as a black box and lets the vendor spawn the maker/checker/evaluator inside the run (that is also what keeps it portable — we don’t reimplement orchestration per vendor). The maker/checker split therefore lives in the loop’s skill, not the scheduler. We still get visibility because the harvester parses sub-agent trees and costs out of the vendor logs, but we do not orchestrate them centrally. Where the split needs different frontier models per role (a GPT implementer + an Opus reviewer), the design offers two routes — intra-run sub-agents (cross-provider native on Cursor) or inter-stage composition by the control plane — see Multi-model loops. If we later want cross-loop sub-agent reuse (one shared “security reviewer” agent), that would be a future addition.

What this design adds beyond the six

The six primitives describe a single loop. This design’s real contribution is the fleet layer on top of them — the things the field guide’s monitoring and maturity sections ask for but no single primitive provides:

Portability across vendors The adapter seam makes all six primitives vendor-neutral — the field guide notes the primitives exist in every tool; this design lets one loop use them on any tool.
Declared dependencies + validation Every primitive a loop needs (tools, auth, env, upstream loops) is declared and checked before deploy — not discovered at 3am.
Inter-loop dependency graph The primitives are within-loop; this adds the between-loop DAG (who feeds whom) inferred from the I/O contract.
Promotion + observability The earned observe→propose→act lifecycle and the cross-vendor UI (fleet, timeline, inbox) operationalize the field guide’s L4 “operating system” rung.
Verdict: the design implements all six primitives — four owned outright (automations, worktrees via the adapter, connectors, state), skills as a vendor-neutral artifact, and sub-agents delegated-but-observed — and then adds the fleet-level layer (portability, dependency graph, promotion, monitoring) that a single loop’s anatomy does not cover. The honest gap is central sub-agent orchestration, which is deliberately left to the runtime to preserve portability.

Tech Stack

Core / CLI Python (Typer CLI). Easy to wrap nv-tools and the vendor CLIs; good MCP and subprocess story.
Scheduler systemd timers + a small supervisor daemon for event/artifact triggers. No external queue in v0.1.
State Git repo (markdown/JSONL) as truth; SQLite for run history/metrics; Linear via nv-tools.
API + UI FastAPI (REST + WebSocket) over SQLite + the memory tree; React frontend with vis-timeline (Gantt) and Cytoscape/d3-force (DAG).
Reuse, don’t reinvent: the harvester deliberately mirrors how the community Claude/Codex monitors already parse ~/.claude/ and ~/.codex/. The genuinely new parts are the cross-vendor normalization, the manifest-driven scheduling, and the artifact-inferred dependency graph.

Build Plan & Milestones

An incremental path: each milestone is independently useful, and the order front-loads the lowest-risk, highest-leverage pieces (the core run path and read-only observability) before anything that mutates remote state. Expand each for scope, deliverables, dependencies, exit criteria, and risks.

M1 — Manifest + Codex adapter + one loop

Prove the core run path end to end on a single vendor with the simplest loop.

  • Convenience layer: a Makefile that wraps the common loopctl calls so day-to-day use is one short command — great for muscle memory and for CI/automation to call uniformly.
  • First loop: slack-triage (L1) — observe-only, single connector, no dependencies.

  • Exit criteria: make run LOOP=slack-triage writes state/slack/triage-latest.md + a run record to the memory tree.

M2 — Scheduler + auth + apply (deploy L1 + L2)

Turn one-shot runs into a scheduled, unattended fleet on the VM.

  • Build: loopctl init (bootstrap host, source + memory trees), loopctl auth (guided creds), loopctl apply (render systemd timer/service units, register event/artifact triggers); pre-deploy dependency validation (auth/env/tools/upstream loops + DAG cycle check). Plus loopctl remove <loop>/--all — the inverse of apply that disables the trigger and deletes a loop’s installed + staged units — and loopctl fleet, a terminal table of every loop with its trigger, last run, and install state (installed/staged/no), the read-only precursor to the M4 web fleet board.
  • Deploy: L1 (slack-triage) + L2 (paper-discovery), both pure observe, on cadence. Includes the L2 prototype migration off per-tool SQLite onto the unified store.
  • Depends on: M1.
  • Exit criteria: L1 + L2 fire on schedule with the laptop closed; an unmet dependency is reported at apply, not at runtime.
  • Risks: VM provisioning + secret placement (outside both repos); systemd Persistent=true catch-up behavior.
M3 — Claude + Cursor adapters (portability)

Make the runtime a config value, not a rewrite — the core portability proof.

  • Build: the Claude and Cursor Runner implementations; loopctl vendor set + per-loop runtime.vendor override; preflight capability checks (tools mappable, auth present, model available).
  • Depends on: M1 (the adapter interface).
  • Exit criteria: an existing loop runs unchanged on Codex and Claude; a vendor swap is one flag. Cursor ships as a limited single-run adapter — it has no writable-root grant yet, so a loop that writes ledger (state/…) outputs is reported unsupported for Cursor at preflight. Full Cursor parity (writable roots) and the cross-provider sub-agent capability move to M3.5.
  • Risks: Cursor CLI per-sub-agent model caveats (plan-dependent); Codex/Claude cross-provider needing a gateway; normalizing results across three log formats.
M3.5 — Multi-model loops

Enable per-role models (maker/checker on different providers).

  • Build: the roles: manifest block; the agent-definition compiler (role def → .codex/.claude/.cursor agent formats); both execution paths — intra-run sub-agents (native on Cursor) and inter-stage composition across adapters via the memory ledger; the Cursor writable-root grant so ledger-writing loops run under Cursor (parity carried over from M3).
  • Depends on: M3 (adapters).
  • Exit criteria: a maker/checker loop runs a gpt-5.5 implementer + an opus reviewer and hands the diff between stages cleanly; a Cursor loop spawns a cross-provider sub-agent; a ledger-writing loop runs unchanged under Cursor.
  • Risks: passing context/diffs across stages without loss; two-model token cost; verifying the readonly reviewer can’t mutate.
M4 — Harvester + fleet board + timeline

First observability: see every loop and run across vendors on one screen.

  • Build: the harvester (watch ~/.codex, ~/.claude, the memory tree; normalize runs into the single SQLite); the read-only web UI — fleet board + Gantt timeline; the REST/WebSocket API.
  • Depends on: M2 (runs exist to harvest).
  • Exit criteria: every run from every vendor appears with status, last/next run, and rolling cost; the timeline shows the nightly cluster and any gaps.
  • Risks: cross-vendor log-format drift; accurate per-vendor cost/pricing tables.

What goes in the SQLite DB (and why it isn’t a second source of truth)

The DB holds operational telemetry only — not loop content. One row per run plus a few derived tables: run_id, loop id, vendor/model, start/end + duration, status (done/stalled/failed/needs_approval), tokens + cost, iteration count, exit code, a pointer to the log, the artifacts touched, and the inferred loop-to-loop edges. It deliberately does not store the findings, summaries, queues, or reports — those live in the ledger and artifact store.

It’s a derived index, so there is no sync problem. The DB is a one-way projection built by the harvester from the vendor logs (~/.codex/~/.claude) and the memory tree’s run records + file mtimes. Data flows logs/ledger → DB, never back. The ledger (git) stays the single source of truth; the DB is a fast, queryable cache for the UI. Because it’s purely derived, it is rebuildable from scratch — loopctl reindex drops and repopulates it from the logs + ledger, so a corrupt or deleted loopcraft.db is a non-event, not data loss. That is exactly why it’s safe to keep it out of git (or git-ignored in the memory tree).
The one nuance — vendor logs are ephemeral. ~/.codex/~/.claude can be rotated/pruned by the vendors, so a pure log-derived DB could lose old history. Fix: each run also writes a small durable run record to the ledger (ledger/runs/<run_id>.json) at finish — that, not the vendor log, is the authoritative input the harvester reindexes from. So the ledger remains complete and the DB is always reconstructable from it alone.
M5 — Dependency DAG + Linear sync (add L3)

Show how loops interact, and wire the human surface.

  • Build: infer the loop DAG from inputs/outputs + observed file accesses; render the interaction graph; bidirectional Linear sync via nv-tools (findings → issues, status/approval → back).
  • Deploy: L3 (eod-summary), the first loop with an upstream dependency (consumes L1).
  • Depends on: M4 (UI) + M2 (loops).
  • Exit criteria: the graph shows the L1→L3 edge; a finding becomes a Linear issue and marking it Done writes back to the ledger.
  • Risks: idempotent finding_id ↔ issue_id mapping; Linear (via nv-tools) rate limits.
M6 — The approval inbox (the human-in-the-loop core), then L4

The inbox is the headline deliverable of this milestone — it is where the whole system meets the human. Everything a loop can’t do unattended lands here, and nothing irreversible happens without a click. It is also the single surface that makes propose-tier loops (and tier promotion) actually usable, so it gets built first in M6 and the rest hangs off it.

The inbox — primary work of M6

  • One unified queue of everything needing you: approval requests, review items, follow-ups, and alerts — across all loops and all vendors, deduplicated, newest/most-urgent first.
  • One-click actions per item: Approve & run / Reject / View diff / Snooze — with a keyboard-driven triage flow so clearing the inbox is fast.
  • Full context inline: each item links to its ledger finding, the produced artifact (report/diff), the source run + logs, and the mirrored Linear issue — so you decide without leaving the screen.
  • Mirrored to Linear (from M5) so the same queue is actionable on mobile and shows up in your normal workflow; state stays in sync both ways.
  • Filter & group by loop, type, tier, and age; an empty inbox is the “all clear” signal.

Supporting plumbing

  • Loop-boundary release steps (perform an approved anticipated action) and the guarded tool proxy + executor (queue mid-run gated calls, execute on approval) — both feed items into the inbox and act on its decisions.
  • Then build L4: the multi-model build → review → iterate → ship loop — branch-per-ticket, draft-MR, fully gated through the inbox. L4 is the first heavy consumer of the inbox, which is why it comes after it.
  • Depends on: M3.5 (multi-model), M5 (Linear sync), M2.
  • Exit criteria: the inbox shows a live, cross-loop queue; approving an item releases the gated action and rejecting discards it; a mid-run gated tool call appears as a pending item rather than executing; L4 opens a draft MR on a feature branch and never touches main.
  • Risks: inbox signal-to-noise (must not become a dumping ground — default to surfacing only what truly needs a human); tool-proxy coverage (no bypass path); evidence-based promotion/auto-demotion.
M7 — Health & alerts

Make the always-on fleet trustworthy to walk away from.

  • Build: stalled-run detection, budget alerts, starved-downstream flags, daily credential-health checks, and notifications — delivered as a Slack DM via nv-tools (plus the inbox) so alerts reach you off the dashboard.
  • Depends on: M4 (harvester history).
  • Exit criteria: a hung run, an exhausted budget, an expired token, and a broken upstream chain each raise a timely alert (Slack DM + inbox).
  • Risks: alert-noise tuning — too noisy and it gets ignored, too quiet and silent failures slip.
M8 — Event triggers & webhooks (reactive loops)

Move beyond cron + artifact-mtime polling to real-time triggers — high-value because it makes loops reactive instead of waiting for the next tick.

  • Build: a webhook ingress on the always-on VM that maps inbound events to loop runs — a new/updated MR or pipeline status (GitLab), a Slack mention/DM (events API), a new Linear issue, or a generic webhook. Extends the existing cadence.type: event the manifest already supports; the supervisor dispatches the matching loop with the event payload as input.
  • Payoff for the initial fleet: L1 triages the moment you’re mentioned instead of at the next 4-hour tick; L4 kicks off the build/review/ship loop the instant a ticket is labeled or assigned — turning the backlog into a true work queue.
  • Depends on: M2 (scheduler/supervisor) + M6 (so reactive write-actions still flow through approvals).
  • Exit criteria: labeling a ticket triggers L4 within seconds; an @mention triggers L1; webhook auth + replay protection in place; polling remains the fallback when no webhook source exists.
  • Risks: webhook delivery reliability (need idempotency + dedup against the ledger’s seen state); securing the public ingress; avoiding trigger storms (debounce/coalesce bursts).
First usable slice: M1–M2 already give you scheduled, headless loops writing to the memory tree — the rest layers portability, observability, and approvals on top. You get value before the UI exists.

Security, Secrets & Failure Modes

Per-host secrets The VM holds its own credentials (nv-tools auth, vendor API keys, git tokens) — never the laptop’s. Secrets live outside both trees (e.g. systemd EnvironmentFile with locked perms or a secrets manager); manifests reference names, not values.
Least privilege per loop A loop only gets the auth/tools it declares. Scoped tokens where possible; write access limited to its own state namespace.
Irreversible = gated Sending, merging, spending always route through the approval inbox — at the loop boundary or, mid-run, via the guarded tool proxy. The control plane has no path to do them unattended.
Budgets cap blast radius Per-loop turn/token/runtime/failure caps. An uncapped loop “does not eventually succeed; it eventually drains the account.”
Always-on cuts both ways A runaway loop on the VM runs all night, not just until you close the laptop. Hence hard caps, stalled-run detection, and a kill switch (loopctl pause <loop> / loopctl pause --all).
Auth expiry is the #1 failure Expired nv-tools/git tokens silently break loops. preflight + a daily credential-health check catch it early — and the check sends you a Slack DM via nv-tools (the one connector most likely to still be valid) the moment any credential is missing or expiring, so you re-auth before the nightly run fails rather than after.
Comprehension debt is a system risk, not just a personal one. The loop-detail view (manifest + diff + logs) exists so the operator actually reads what shipped. A loop that no one ever reviews should be demoted to a louder review cadence, not left running on faith.

Open Questions & Future Work

  • Cross-host loops. Some loops may want the vendor cloud (locus: cloud) instead of the VM. The adapter abstraction should extend to a cloud runner without changing manifests.
  • Cost attribution accuracy. Normalizing token/cost across Codex and Claude pricing needs a per-vendor pricing table; “cost per accepted change” is the metric we actually want to surface.
  • The research pipeline (W8/W9). Paper-discovery (L2) is the funnel; the reading/summarization and experiment-generation loops are the obvious next additions once the plane is solid.
  • Self-evolving loops. A meta-loop that proposes manifest edits (cadence, budget, even new loops) is the L5 frontier — powerful, but it must stay propose-tier and human-approved.
  • Multi-operator / team. Out of scope for v0.1, but the Linear board already hints at how shared review could work.

Appendix — Glossary

TermMeaning
Control planeThe system that declares, schedules, runs, and monitors loops (this proposal). It orchestrates; the vendors execute.
ManifestThe YAML file fully describing one loop: logic, dependencies, locus, cadence, tier, budget, I/O.
Runtime adapter / RunnerVendor-specific code that runs a vendor-neutral loop on Codex or Claude and normalizes the result.
LocusWhere a loop executes: vm (default, always-on), cloud, or local.
TierAutonomy level: observe (read-only) / propose (drafts for approval) / act (executes within budget).
Memory tree~/workspace/loopcraft_memory — the separate repo holding all memory (ledger/ + artifacts/ + SQLite), distinct from the source tree.
State ledgerThe git-versioned markdown/JSONL collection (loopcraft_memory/ledger/) holding loop memory — the system’s source of truth.
Artifact storeProduced files (reports, diagrams, charts, PDFs, exports) under loopcraft_memory/artifacts/ — same git repo, git-LFS for big blobs (object-store offload optional), with provenance manifests in git.
HarvesterThe component that reads vendor logs + artifacts into SQLite and infers the dependency graph.
Release stepThe bounded follow-up invocation that performs a loop’s anticipated action after a human approves it (loop-boundary approval).
Guarded tool proxyThe MCP shim / nv-tools wrapper that all tool calls route through; auto-runs reads, queues gated writes/sends for approval, and executes them post-approval (tool-call-level approval).
nv-toolsThe unified NVIDIA developer CLI (Jira, Slack, GitLab, Gerrit, Confluence, Linear, …) used as the vendor-agnostic connector layer — including the Linear access the state store uses.
