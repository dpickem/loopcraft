What Loop Engineering Is

Loop engineering is replacing yourself as the person who prompts the agent. Instead of holding the tool one turn at a time — type, read, type again — you design a system that does the prompting and decides the next move on its own. A “loop” is a recursive goal: you define a purpose and a stopping condition, and the agent iterates until it is complete.

The shift from prompting to loops

The old model was conversational and synchronous. You were the orchestrator, the dispatcher, and the verifier, every single turn. That works, but it caps throughput at one human attention span. The loop model externalizes the orchestration: the loop runs on a timer, spawns helpers, feeds itself the next task, and only escalates to you when it cannot proceed or when something needs judgment.

Osmani frames it as a stack: harness engineering is building the environment a single agent runs inside (the factory). Loop engineering sits one floor above — it is the harness, but it runs on a timer, spawns little helpers, and feeds itself.

What a loop is not

  • Not a single run you did once. A one-shot agent task is not a loop. The cadence is what makes it a loop.
  • Not “fire and forget.” A loop running unattended is also a loop making mistakes unattended. The verifier and the memory are non-negotiable.
  • Not a replacement for understanding. The loop changes the work; it does not delete you from it. You move from operator to designer, not to spectator.

Why Now — The Inflection Point

A year ago a loop meant a pile of bespoke bash you owned and maintained forever. What changed is that the primitives now ship inside the products. Steinberger’s list of what a loop needs maps almost one-to-one onto the Codex app, and nearly the same onto Claude Code and Cursor. Once you notice the shape is identical across tools, you stop arguing about which tool and just design a loop that survives whichever one you happen to be sitting in.

The capabilities converged Scheduling, worktrees, skills, MCP connectors, and sub-agents are now first-class features, not weekend scripts. The names differ; the capability is the same.
The cost model is real Loops run agents while you sleep, so token spend can vary wildly. This is a genuine constraint — budget it, cap it, and spend sub-agents only where a second opinion pays for itself.
The bottleneck moved to you Worktrees remove the mechanical collisions of parallel agents, but your review bandwidth is still the ceiling on how many loops you can actually run.
Skeptic’s footnote (worth keeping): even the people most bullish on this are careful. Osmani is explicit that it is early, that token costs bite, and that two people building the exact same loop get opposite results depending on whether they use it to move faster on work they understand or to avoid understanding the work at all.

Anatomy of a Loop — Five Primitives + Memory

A loop needs five moving parts and one place to remember things. Here is the canonical list, with the job each part does and how it shows up across the three tools you are likely to use.

1. Automations — the heartbeat

Automations are what make a loop an actual loop and not just one run you did once. You define a prompt, a cadence, and an environment (your local checkout or a background worktree). Runs that find something land in a triage inbox; runs that find nothing archive themselves. Typical jobs: daily issue triage, summarizing CI failures, writing commit briefings, hunting last week’s regressions. An automation can call a skill, so you fire $skill-name instead of pasting a wall of instructions into a schedule nobody will ever update.

Two in-session control primitives worth knowing: /loop re-runs a prompt on a cadence; /goal keeps going until a verifiable stopping condition is true, with a separate small model checking “are we done?” after every turn — so the agent that wrote the code is not the one grading it. Both Codex and Claude Code ship a /goal; Cursor exposes the same idea through its loop/automation tooling.

2. Worktrees — parallel without chaos

The moment you run more than one agent, files start colliding — the same headache as two engineers committing to the same lines without talking. A git worktree is a separate working directory on its own branch sharing the same repo history, so one agent’s edits literally cannot touch another’s checkout. Codex builds worktrees in per thread; Claude Code gives you git worktree, a --worktree flag, and an isolation: worktree setting on sub-agents; Cursor supports per-agent worktrees too.

3. Skills — stop re-explaining your project

A skill is how you stop re-explaining the same project context every session like a goldfish. It is a folder with a SKILL.md holding instructions and metadata, plus optional scripts, references, and assets. The agent runs it when you call it explicitly or when your task matches its description — which is why a tight, boring description beats a clever one. Skills are where intent stops costing you over and over: the conventions, the build steps, the “we don’t do it like this because of that one incident” get written down once where the agent reads them every run. Without skills, the loop re-derives your whole project from zero every cycle; with skills it compounds.

4. Plugins & connectors — touch your real tools

A loop that can only see the filesystem is a tiny loop. Connectors (built on MCP) let the agent read your issue tracker, query a database, hit a staging API, drop a message in Slack. Plugins bundle connectors and skills so a teammate installs your whole setup in one go. This is the difference between an agent that says “here is the fix” and a loop that opens the PR, links the ticket, and pings the channel once CI is green by itself. At NVIDIA, your single biggest connector is nv-tools (Jira, Confluence, Slack, Gerrit, Helios, GDrive, W&B, and more behind one CLI).

5. Sub-agents — keep the maker away from the checker

The most useful structural move in a loop is splitting the one who writes from the one who checks. The model that wrote the code is far too generous grading its own homework; a second agent with different instructions (and sometimes a different model) catches what the first talked itself into. The usual split is one agent explores, one implements, one verifies against the spec. Sub-agents burn more tokens because each runs its own model and tools, so spend them where a second opinion is worth paying for. This is also what /goal does under the hood: a fresh model decides whether the loop is done.

6. Memory / state — the spine

The sixth thing is the one that sounds too dumb to matter: a place to remember stuff that lives outside the single conversation. A markdown file, a Linear board, an Obsidian note — anything on disk that holds what is done and what is next. The model forgets everything between runs, so the memory has to be on disk, not in the context. The agent forgets; the repo does not. This is what lets tomorrow’s run pick up where today’s stopped.

The Control Loop — How a Loop Actually Runs

Stick the primitives together and a single thread becomes a small control panel. Every loop, whether it ships code or rebalances a paper portfolio, walks the same cycle:

1. Discoverautomation finds work
2. Triagerank, filter, decide worth-doing
3. Dispatchworktree + maker sub-agent
4. Verifychecker sub-agent vs. spec
5. Actconnector: PR, ticket, message
6. Recordwrite outcome to memory
7. Decide nextresume tomorrow from state

A worked example, in one paragraph

An automation runs every morning on the repo. Its prompt calls a triage skill that reads yesterday’s CI failures, the open issues, and the recent commits, and writes the findings into a markdown file or a Linear board. For each finding worth doing, the thread opens an isolated worktree and sends a sub-agent to draft the fix; a second sub-agent reviews that draft against the project skills and the existing tests. Connectors open the PR and update the ticket. Anything the loop cannot handle lands in the triage inbox for you. The state file is the spine: it remembers what was tried, what passed, what is still open — so tomorrow’s run picks up where today’s stopped. You designed it once. You prompted none of those steps.

The stopping condition is the hard part. “Done” must be verifiable: “all tests in test/auth pass and lint is clean,” not “the feature works.” If you cannot write the stop condition as something a separate model can check, the loop has no business running unattended.

Addy Osmani — Loop Engineering (the definitive map)

Core thesis. “Loop engineering is replacing yourself as the person who prompts the agent. You design the system that does it instead.” A loop is a recursive goal: you define a purpose and the AI iterates until complete. Osmani is openly skeptical and stresses it is early and token-cost-sensitive — but believes it may be the future of working with coding agents.

The two anchor quotes

  • Peter Steinberger (OpenClaw creator, now at OpenAI): “You shouldn’t be prompting coding agents anymore. You should be designing loops that prompt your agents.”
  • Boris Cherny (head of Claude Code, Anthropic): “I don’t prompt Claude anymore. I have loops running that prompt Claude and figuring out what to do. My job is to write loops.”

Key concepts

  • The stack: prompting → harness engineering (the environment one agent runs inside) → loop engineering (the harness, but on a timer that spawns helpers and feeds itself).
  • Five primitives + memory: automations, worktrees, skills, plugins/connectors, sub-agents, and an external state file. He argues all five now ship inside both Codex and Claude Code, and gives a primitive-by-primitive mapping table.
  • Automations are the heartbeat: distinguishes /loop (re-run on a cadence) from /goal (run until a verifiable stop condition holds, with a separate small model grading “are we done?” each turn).
  • Memory is the spine: the model forgets between runs, so state must live on disk — “the agent forgets, the repo doesn’t.”
  • Maker ≠ checker: the model that wrote the code grades its own homework too kindly; a separate verifier sub-agent is what lets you walk away.

The setup he describes

A single worked loop: a morning automation calls a triage skill that reads yesterday’s CI failures, open issues, and recent commits and writes findings to a markdown file or Linear board; for each worthwhile finding it opens a worktree, a maker sub-agent drafts the fix, a checker sub-agent reviews it against project skills and tests; connectors open the PR and update the ticket; anything it can’t handle lands in a triage inbox. “You designed it once. You did not prompt any of those steps.”

The three pitfalls (his framing)

  • Verification is still on you — “done” is a claim, not a proof.
  • Comprehension debt — the faster the loop ships code you didn’t write, the bigger the gap between what exists and what you understand.
  • Cognitive surrender — the comfortable posture (taking outputs without an opinion) is the dangerous one. Two people build the same loop; one to move faster on work they understand, one to avoid understanding. The loop can’t tell the difference.

Takeaway line: “Build the loop. But build it like someone who intends to stay the engineer, not just the person who presses go.” He also threads in his related essays — harness engineering, intent debt, the orchestration tax, long-running agents, adversarial code review.

Rahul (@sairahul1) — Loops: What Every AI Engineer Needs to Know in 2026

Core thesis. Loops are the new baseline competency for AI engineers in 2026. The piece opens on both anchor quotes — Steinberger (“stop prompting… design loops that prompt your agents”) and Cherny (“my job is to write loops”) — calls them “two of the most senior AI engineers alive” saying the same thing, and then builds the full mental model from first principles. It is the most complete practitioner breakdown of the set (~4.6M views).

The blocker it leads with: cost

Its most distinctive move is putting the economics first — the reason most people never build loops. A single agent loop on a medium task burns ~50K–200K tokens; a fleet loop with an orchestrator + 3 specialists, 500K–2M; a daily scheduled loop, millions per week. Every retry, self-correction, subagent, and verification pass costs. The takeaway: “Loops are not hard to design. They are hard to afford.” It argues cheap frontier models (e.g. DeepSeek V4, Kimi, MiniMax) are what make loops economically viable, and that a large context window matters because loops need to hold previous runs, errors, architecture docs, and test results in memory at once.

Open loops vs closed loops (its key practical distinction)

  • Open looping — you give a goal and let the agent roam; exploratory and powerful (what labs with unlimited budget do), but it burns tokens and, against loose standards, becomes “a slop machine.”
  • Closed looping — a human designs the end-to-end path first: clear goal, defined steps, an eval at each step, and a stop/handback point. Improves every run, runs on a normal budget, stays honest because of the quality gate.
  • Advice: start with closed loops; open them up only once your quality gates are solid. “Without a quality gate, AI drifts. With one, AI improves.”

Single agent vs fleet

Two scales of looping: a single-agent loop (one brain redoing its own draft — discover, plan, execute, verify, iterate) and a fleet loop (an orchestrator owns the goal, specialists own the steps, subagents do the narrow work, eval gates keep it from being slop). Every agent in the tree runs the same 5-stage loop.

The framework it codifies

  • 5 stages every loop moves through: DISCOVER → PLAN → EXECUTE → VERIFY → ITERATE (pass verification → ship; fail → loop again).
  • 6 building blocks, each mapped to a stage: automations (heartbeat, triggers discover), worktrees (parallel execute without collisions), skills (faster discover — VISION.md, ARCHITECTURE.md, RULES.md), plugins/connectors (real execute via MCP), subagents (honest verify — maker ≠ checker), memory (persistence — run 47 knows what runs 1–46 tried).
  • 5 parts of a good loop: a precise goal (what “done” means), context (the .md files), action (only what the agent needs), feedback (tests, type checks, linters, structured errors), and a stop condition.

Concrete loop templates it gives

Worked skeletons for a coding loop (read vision/arch → plan → edit → test → fix-on-fail → summarize), a research loop (question → search → summarize → verify claims → synthesize → stop at confidence threshold), a content loop (draft → critique agent → rewrite → score → publish/repeat), and a sales-outreach loop. Common skeleton: Goal → Action → Check → Fix → Repeat until done.

Prompt engineer vs loop engineer

The skill gap it names: a prompt engineer crafts better instructions and reviews each output by hand (you are the feedback loop); a loop engineer designs feedback cycles where the system runs, checks, and self-corrects (the system is the feedback loop). “Prompt engineers ask AI for output. Loop engineers design systems that produce verified outcomes.” It ends on the same note as Osmani — two people build the same loop and get opposite results; the loop can’t tell the difference, you can — “build it like someone who intends to stay the engineer, not just the person who presses go.”

Use it for: the economics of loops (open vs closed, token budgets), the single-vs-fleet decision, and ready-made loop skeletons. Its tagline: “one reliable loop is worth a thousand perfect prompts.”

elvis (@omarsar0) — From Prompting Agents to Loop Engineering

Core thesis. The “practical version” of the claim — what an agent loop is, why it matters, and what one looks like in production. It grants that the idea “gets repeated often and explained rarely,” then does the explaining, drawing on experiments and conversations with founders, AI engineers, and startups. Its framing of the shift: the work moves up a level, “from writing the code to writing the system that writes the code” — with developers reporting months where they shipped hundreds of PRs without opening an IDE.

What a loop actually is

A small program that does four things: prompts the agent for you, reads what it produced, decides whether it is done, and if not, prompts again with the error or next step. “You write the loop, and the model becomes a subroutine it calls.” Shape: set a goal, act, check, feed the error back, repeat until the check passes or the loop stops itself.

“Loop” means at least five things (its clearest contribution)

It untangles the word by tracing the lineage, oldest to newest: ReAct (2022, reason–act–observe–repeat) → AutoGPT (2023, self-prompting goal loop that never knew when to stop) → the ralph loop (deliberate context reset between iterations so the agent doesn’t drown in its own history) → /loop and /goal (cadence and completion conditions built into the agent, state carried across turns) → orchestration (one author fans out many agents that read GitHub/Slack/chat and decide what to build next).

The six parts you assemble

Same anatomy, named operationally: a trigger (schedule/webhook/file-change/label — what separates a real loop from a repeated run), isolation (a worktree per agent), written-down context, reach into your tools (connectors), a second agent that checks (held apart from the maker), and state on disk.

The contracts and recipes it adds

  • The PR babysitter — a buildable-today loop: trigger every 15 min, scope to PRs labeled agent-watch, one fix attempt / 5 min / 10 files, stop on green CI or budget. Same shape covers CI-health clustering, deploy verification, and feedback clustering.
  • /goal as a contract — a strong goal specifies four things: the end state, the evidence that proves it, the constraints not to break, and the work budget. “npm test exits 0 is a goal; ‘make it better’ is not.” An independent evaluator (a fast model) decides met/not-met so the agent doesn’t grade itself.
  • Roles as an architecture decision — once you split planner / executor / evaluator / vision-reviewer, each can run on a different model; you swap per role instead of betting on one “best” agent.
  • Cherny’s 5-step autonomous setup — auto-approve permissions, dynamic workflows to fan out, /goal or /loop to keep going, run in the cloud, and give it end-to-end self-verification (Chrome for web, simulator MCP for mobile, live server for backend) — the step that makes the other four safe.
  • crabfleet (Steinberger’s OpenClaw “mission control”) — orchestration hardened into a product: work as cards on a board (todo → running → human review → done), durable runs with heartbeats, agents that spawn agents, on disposable cloud sandboxes.

Where the cost goes now

Its sharpest reframing: inside a loop, spend is no longer “which model, how many tokens” but how many times the loop goes around. So: iterations are the budget line (track cost per finished task, not per call); a weak verifier is the most expensive bug you can ship (it stops early on broken work or grinds on fine work); and failing fast is a cost control (an uncapped loop drains the account). “You used to tune the prompt; now you tune the loop.”

When not to loop & what goes wrong

Skip loops for one-shot edits, unscoped/exploratory work with no pass condition, and anything without a cheap automated check (“if the only verifier is your own eyes, you are still inside the loop”). Failure modes are predictable: the verification burden stays human, comprehension gaps widen, and a loose check causes silent drift — “why the engineer who designs the loop matters more, not less.”

Use it for: the clearest taxonomy of what “loop” means, the /goal-as-contract discipline, the per-role multi-model idea, and the “cost = iterations” reframing. Plus a concrete 6-step “how to build your own.”

AlphaSignal AI — All about loop engineering (including the pitfalls)

Core thesis. The anatomy of a production-ready loop in 5 minutes, plus how to keep it from spiraling. Adapted from @bendee983’s AlphaSignal Sunday Deep Dive on “the gap between AI code generation and actual software delivery,” anchored on the Steinberger and Cherny quotes. Its sharpest line: “the best AI engineering skill is no longer crafting a perfect LLM prompt but engineering loops with LLMs at their heart.”

What loop engineering is (its definition)

It shifts a model “from a static call-and-response tool to an active participant in an event loop.” You give the system a verifiable goal; the loop observes state, chooses an action, executes, checks the result, and decides whether to continue, retry, or stop. It explicitly adopts Osmani’s five primitives (automations, worktrees, skills + external tools, sub-agents, memory) in simplified form, and cites Karpathy’s autoresearch — a lightweight Python loop running ML experiments overnight — as the proof-of-concept.

The trap: “loopmaxxing” is the new “tokenmaxxing” (its signature idea)

The piece’s distinctive contribution is naming the anti-pattern. Just as tokenmaxxing brute-forces answers with massive inference budgets, loopmaxxing replaces real architecture with open-ended while(true) iteration on the assumption the agent will “eventually figure it out.” Two ways it bites:

  • Infinite drift on fuzzy goals. “Refactor this to be better” has no exit condition, so the agent spins into endless retries, optimizing hallucinated metrics and burning millions of tokens on memory/context a human would just retain.
  • Comprehension debt. As the loop ships code in the background, the gap widens between the repo’s state and the engineer’s understanding — so when production breaks, debugging becomes “an observability nightmare,” staring at thousands of lines of unfamiliar logic with no mental model of why the agent chose that path.

The pragmatic path: strict control loops, not open-ended cycles

  • Deterministic code drives; the LLM only decides. Developers write the desired state and the observation mechanism; ordinary code handles execution and API calls; the LLM step is reserved for dynamic decisions traditional code can’t make — wrapping risky parts in memory and hard-coded checks to “limit the blast radius of a hallucinating model.”
  • Start minimal with human verification, run it several times to learn what works, then gradually replace the LLM steps the agent gets right consistently with standard code.
  • Separate maker from checker — “an agent looping over its own flawed logic tends to reinforce its mistakes rather than fix them.”
  • Production requirements: trace-logging of agent reasoning, progress detection to kill a stuck run, strict iteration caps, and an explicit human-handover point — a rule of thumb of two or three retries before failing gracefully back to a human.

The closing warning

“Cognitive surrender remains the most significant risk” — building a system specifically so you never have to think about your codebase is a recipe for disaster, and no amount of compute saves poor architecture. Its memorable framing: “Agents run loudly and fail quietly” — so stay a vigilant engineer, not just a prompt supervisor.

Use it for: the guardrails mindset — the loopmaxxing anti-pattern, the deterministic-control-loop pattern, and the 2–3-retry handover rule. Maps directly onto this guide’s Guardrails section.

Anatoli Kopadze — Loops explained: Claude, GPT, Mira and what actually works

Core thesis. The accessible, beginner-first explainer (~9.3M views, the highest-reach of the set). It argues most people still use AI “the slowest way there is” — one request at a time, where you are the engine and the AI stops the moment you stop. A loop flips that: you give the goal once and step out. Notably even-handed about when not to bother, and it ends by pointing non-engineers at a no-code option rather than the heavy stack.

The framework

Same five stages (DISCOVER → PLAN → EXECUTE → VERIFY → ITERATE), but it singles out the three that do the real work: Verify is the heart (“no gate means the agent grades its own homework, and the model that did the work is far too generous a grader”), State is what makes the loop learn (remember what was tried, resume instead of restarting), and the Stop condition is what keeps it sane (success or a hard limit). “A prompt hands the AI an instruction. A loop hands it a job, a way to know when the job is done, and a rule for when to give up.”

Its sharpest practical contribution: the “do you even need one?” test

A loop is worth building only when all four are true: (1) the task repeats at least weekly; (2) something can automatically reject bad output (test, type check, build, linter, hard rule); (3) the agent can do it end to end; (4) “done” is objective, not taste. Miss one box — keep it a manual prompt. “Loop engineering is real, and most people do not need the heavy version yet.”

The code version & the cost reality

  • Five building blocks (Claude Code / Codex ship all five): automation (heartbeat), skill (reusable instructions), sub-agents (maker vs. checker — “most of the quality”), connectors (act, not suggest), and the verifier (the gate that decides whether the loop helps or just spends money). Cites a loop rewriting a whole codebase from one language to another in ~6 days.
  • Cost compounds because the full context is re-sent every iteration and grows each pass; maker+checker doubles it. The metric almost nobody tracks: cost per accepted change — below a ~50% accept rate the loop costs more than it gives back.
  • The “Ralph Wiggum loop” (Geoffrey Huntley): the agent decides it’s done too early, exits half-finished, and the loop keeps running and billing while producing nothing. “Loops do not crash, they bill you in silence.”

The build order & a paste-able loop

Order matters more than tools: (1) get one manual run reliable, (2) turn it into a skill, (3) wrap it in a loop with a gate + stop condition, (4) then schedule it — “scheduling something you have not made reliable by hand is exactly how loops blow up while you sleep.” It includes a self-checking PLAN / DO / VERIFY / DECIDE loop you can paste into any LLM today — with the key caveat that you are still the trigger (close the tab and it’s gone).

The “loops for your actual life” angle

Its distinctive turn: for ~99% of everyday tasks you don’t need code/hosting/keys — you need a no-code agent that runs on a schedule or on events. The article recommends Mira (a Telegram-based agent; connects to 500+ apps via Composio, persistent memory, model-agnostic) where you describe a “Skill” in plain words and it acts (“ChatGPT answers, Mira acts”). Examples: a 7am Gmail+Calendar brief, forward-a-message→Linear ticket, meeting pre-briefs, habit/streak check-ins, flight-price watchers, calorie-from-photo. (Note: this part is partly a product promotion; the underlying point — everyday loops via a no-code scheduler-agent — stands regardless of the specific tool.)

Use it for: the four-box “do you even need a loop?” test, the prove-it-by-hand-before-you-schedule order, “cost per accepted change,” and the strongest set of personal / daily-life loop ideas — directly relevant to this guide’s Life Loops section.

Alok Bishoyi (@alokbishoyi97) — Self-Evolving Autoresearch Workflow Loops

Core thesis. The most concrete and frontier entry: a build report on porting evo’s autoresearch loop onto dynamic workflows, then making the loop rewrite itself while it runs. The key conceptual claim — on June 2 Anthropic shipped dynamic workflows in Claude Code, where Claude writes a small JavaScript program on the fly that spawns and coordinates subagents: “orchestration itself moved off the model’s decision and can now be described as code — the model does the judgment, the code does the coordination.”

What evo is

An open-source autoresearch orchestrator (runs on Claude Code, Codex, Cursor). You give it a system, a definition of “better,” and a budget; it generates hypotheses, runs each in an isolated workspace, scores it, and keeps a tree of attempts — extending what works, pruning what doesn’t — while an auditor checks every accepted change so the optimizer can’t game the metric. (Concrete proof of the maker/checker split this guide keeps stressing.)

Why move the loop onto workflows (its central lesson)

The loop used to be orchestrated in-context as one long agent run holding the whole plan. Its hard-won finding: “prompt and instruction adherence is unreliable on long-horizon tasks” — across dozens of rounds the standing rules (run this phase, use this CLI, keep the gate strict) quietly stop happening, and the longer one context runs, the less it holds. Putting the loop in a dynamic workflow fixes it at the root: the method becomes code — phases, fan-out width, stopping rule, gates, CLI calls are deterministic and identical on round 1 and round 1000. Every step is a fresh, scoped subagent with a clean context, so there is nothing to drift.

One round of the loop (six coded steps)

Orient (read the experiment tree, take the top frontier nodes as parents) → Scan (parallel agents find what’s working/failing) → Ideate (on a stall, three research agents: extrapolate the best branch, dissect failures, read the literature) → Brief (fold findings into deduped experiment briefs) → Fan-out (one parallel lane per brief: implement, pre-verify against metric-gaming, run, post-audit) → Collect (prune dead lineages, record notes, repeat until the score stalls).

The self-evolving part (evo 0.5)

  • Two async loops on one event loop (joined with Promise.all): the optimize loop (the driver) and a concurrent meta loop — a fresh agent that wakes every few minutes, reads the run from the outside, and rewrites the optimize loop while it runs.
  • They share one plain object, the harness (the steps, phases, prompts, gates, verifiers, plus knobs like width/stall). The optimizer reads it each round; the meta thread writes it — writes land between the optimizer’s awaits, no locks, no second process.
  • The meta emits four outputs: harness edits (the real lever — inject a verifier step an experiment class needs, cut dead-weight phases, rewrite the phases that run; “the loop’s shape becomes data the system changes”); brief hints (softer nudges for the next round); stops (never a silent kill — it recommends to a separate gated enforcer that verifies, aborts, diagnoses, discards); and alerts (runtime problems like a dying GPU go to a human).
  • Finding: an external observer / meta agent nudging the run is “very effective in course-correcting and catching issues.”

The takeaway it lands

Dynamic workflows make coordination code instead of context, so the loop becomes a first-class object you can read, edit, and reason about while it runs — and “the loop’s own shape is one more parameter space that can be evolved.” This is exactly the L5 rung of this guide’s maturity model; note that even here the meta agent is strictly read-only and hands kills/alerts to gated enforcers or humans — the judgment layer does not move.

Use it for: the strongest argument that long-horizon loops should be code, not prompts; the concrete meta-loop pattern (observer rewrites the harness between awaits); and a real-world maker/checker/auditor design. evo is open source.

What the sources agree on, unanimously: the anatomy (six parts), the maker/checker split, the external memory, and the warning that loops magnify the operator. Where they differ is mostly emphasis — Osmani on completeness, Rahul on economics (open vs closed loops, token budgets) and the full framework, elvis on the “loop” taxonomy and cost-as-iterations, AlphaSignal on guardrails (the “loopmaxxing” anti-pattern and control loops), Kopadze on accessibility (the “do you even need one?” test and everyday/life loops), and Bishoyi on the self-evolving frontier.

Lessons Learned & Pitfalls

The uncomfortable truth from everyone who has run loops in anger: the three biggest problems get sharper as the loop gets better, not easier. A smooth loop is a more dangerous loop if you stop paying attention.

Pitfall 1 — Verification is still on you

A loop running unattended is a loop making mistakes unattended. Splitting a verifier sub-agent from the maker is what makes the loop’s “it’s done” mean something — but even then, “done” is a claim, not a proof. Your job is to ship work you confirmed, not work the loop asserted.

Pitfall 2 — Comprehension debt

The faster the loop ships work you did not write, the bigger the gap between what exists and what you actually understand. A smooth loop just makes that gap grow faster. The mitigation is boring and non-negotiable: read what the loop made, on a cadence, even when it “passed.”

Pitfall 3 — Cognitive surrender

When the loop runs itself it is tempting to stop having an opinion and just take whatever it returns. Designing the loop is the cure when you do it with judgment, and the accelerant when you do it to avoid thinking. Same action, opposite result. Osmani’s line is the test: two people build the identical loop — one to move faster on work they understand deeply, one to avoid understanding the work at all. The loop does not know the difference. You do.

Practical lessons that prevent leaks

Tight, boring skill descriptions A skill fires when its description matches the task. Clever descriptions misfire; boring, specific ones win.
State on disk, never in context If the loop’s memory lives only in a conversation, it dies when the conversation does. Write it to a file or a board.
Verifiable stop conditions only If a separate model cannot check “done,” the loop should escalate to a human, not declare victory.
Budget tokens explicitly Loops spend money while you sleep. Cap run frequency and reserve sub-agents for where a second opinion pays off.
Inbox, not auto-merge, at first Until you trust a loop, have it propose into a triage inbox. Promote it to autonomous action only after a track record.
You are the throughput ceiling Worktrees let you run many agents, but your review bandwidth caps how many loops are actually safe to run.

How We Use This — A Design Method

The hardest part is not the concept; it is mapping it onto daily, useful, compounding workflows. Here is a repeatable method for turning any recurring chore into a loop. Run a candidate through these seven questions before you build it.

The Loop Design Canvas

#QuestionWhat you are deciding
1What recurring work do I keep doing by hand?The trigger — only loop things that actually repeat.
2How often, and on what signal, should it run?The cadence — cron, on-commit, on-failure, on-new-data.
3What does “done” look like, checkably?The stop condition — must be verifiable by a second model.
4What tools must it touch?The connectors — nv-tools, market data, calendar, the vault.
5What project knowledge does it need every run?The skill — conventions, formats, “don’t do X” rules.
6Who checks the work?The verifier — a separate sub-agent / stop-condition check.
7Where does it remember state?The memory — a markdown/JSONL file or a board.

Three escalation tiers (choose per loop)

Tier 1 Observe Read-only. The loop summarizes, ranks, and reports into an inbox or daily note. Zero blast radius. Start every loop here.
Tier 2 Propose The loop drafts the artifact — a PR, a ticket, a rebalance plan, a reply — and parks it for one-click human approval.
Tier 3 Act The loop executes autonomously within hard guardrails, after it has earned trust at Tier 2. Reserve for low-stakes, reversible actions.
Promotion rule: a loop only graduates a tier after it has produced N consecutive runs you would have approved unchanged. Write that track record into the loop’s own memory file so the decision is evidence-based, not vibes.

Work Loops — Nemotron Post-Training

Post-training is unusually loop-friendly: it is a stream of long-running jobs, evals, datasets, and recipes that already produce machine-readable signals. The biggest wins are the coding-adjacent chores that surround the actual research — triage, monitoring, synthesis, bookkeeping — exactly the work that drains attention without needing your taste. Each loop below lists its cadence, the canvas mapping, and a starter prompt.

Loop W1 — Nightly eval-regression triage

Cadence: nightly, after eval jobs land. Tier: 1→2. Connectors: W&B, dashboards, Jira, Slack via nv-tools. Memory: evals/triage-log.md.

The loop pulls the latest eval results, diffs them against the rolling baseline, flags any metric regression beyond a threshold, drafts a short triage note (which checkpoint, which suite, suspected cause from recent recipe/data changes), and files it into the inbox. Promote to Tier 2 once you trust it: it opens a Jira ticket and pings the owner. 

$eval-triage
For each eval suite that ran since the last entry in evals/triage-log.md:
  - compare metrics to the 7-run rolling baseline
  - flag regressions > 1.5% absolute or > 2 sigma
  - cross-reference recent data-blend and recipe commits as suspects
  - append a dated entry: suite, metric, delta, suspected cause, owner
Escalate only regressions; archive clean runs silently.

Loop W2 — Training-run babysitter

Cadence: every 30–60 min while jobs run. Tier: 1→2. Connectors: Slurm/MagLev, W&B. Memory: per-run runs/<job_id>.md.

Watches active runs for divergence, NaNs, throughput cliffs, and stalled steps; writes a one-line health beat each cycle; produces an overnight summary at morning. At Tier 2 it can auto-restart a known-safe failure mode (OOM with a smaller micro-batch) and log what it did. This is the practical, bounded version of Karpathy-style autoresearch: the agent watches, summarizes, and nudges overnight while you sleep.

Loop W3 — Data-quality gate on new shards

Cadence: on new dataset shard / blend artifact. Tier: 2. Connectors: Lustre/DSS, data-quality checkers. Memory: data/qa-ledger.jsonl.

Runs the data-quality checkers on each new shard (schema, dedup, length stats, reward-profile sanity), quarantines bad shards, and writes a pass/fail manifest. A maker sub-agent proposes the fix or filter; a checker sub-agent verifies against the data card spec before anything is registered.

Loop W4 — Daily arXiv + literature digest

Cadence: daily, 7am. Tier: 1. Connectors: arXiv, Glean. Memory: reading-list note in the Obsidian vault.

Scans new submissions on post-training, RLHF/RLVR, distillation, reward modeling, and evals; scores relevance against your current projects; writes the top 3–5 with a two-line “why it matters to us” into the vault, dedup’d against what you have already saved. This compounds into a living, project-aware literature map.

W4 is the lightweight glance. If you want the full pipeline — multi-source discovery, deep summarization, and experiment generation — loops W7–W9 below generalize it into a connected research-intelligence system. Run W4 alone if you just want a daily skim; run W7–W9 if you want a compounding idea engine.

Loop W5 — Standup & status synthesizer

Cadence: daily and weekly. Tier: 1→2. Connectors: Slack, Jira, git, daily notes via nv-tools. Memory: daily notes in the vault.

Pulls your mentions, ticket movement, and commits; drafts a standup blurb and a weekly status; rolls the same evidence forward all year so focal self-assessment is a query, not an archaeology dig. (You already have the building blocks from the nv-tools workflows; the loop just runs them on a cadence.)

Loop W6 — Inbound code-review & PR babysitter

Cadence: on new CL / on CI status change. Tier: 2. Connectors: Gerrit/GitLab via nv-tools. Memory: per-CL thread.

For CLs assigned to you, runs the NDAS review checklist and drafts inline comments for your approval; for your own PRs, keeps them merge-ready by triaging comments, resolving trivial conflicts, and re-running CI until green — escalating only the judgment calls.

The research-intelligence pipeline (W7→W8→W9)

Each loop’s output is the next loop’s input, and each writes to a shared, living artifact in the vault. This is the part of post-training that most rewards a loop: keeping up with the literature and turning it into testable bets is constant, high-value, and the kind of work that silently slips when you are heads-down.

Loop W7 — Multi-source paper discovery

Cadence: daily, 7am. Tier: 1. Connectors: arXiv API, X/Twitter (curated lists + follows), newsletter inbox (Outlook/Gmail), RSS, Glean. Memory: research/discovery-queue.jsonl + a research/seen.json dedup set.

Most papers worth reading do not reach you through arXiv first — they arrive via a researcher’s post, a newsletter, or a colleague’s link. W7 fans out across all of those, normalizes every hit to a common record, deduplicates the same paper arriving from three places, scores it against your active themes, and drops the keepers into one queue. It is the funnel; it never reads the papers (that is W8).

What each source contributes

  • arXiv: new submissions in cs.CL, cs.LG, cs.AI filtered to post-training, RLHF/RLVR, distillation, reward modeling, evals, agentic.
  • X/Twitter: extract paper/blog links from posts by a curated list (frontier labs, researchers you follow); keep the surfacing tweet as context (“why it’s buzzing”).
  • Newsletters: parse the emails you already subscribe to, pull out linked papers, and strip the marketing.
  • RSS / Glean: lab blogs, conference proceedings, and internal mentions for anything the public sources miss.
Living artifact: a single deduplicated discovery queue where every item carries {title, authors, url, source, date, abstract, surfaced_by, relevance, why} — so you stop re-finding the same paper and always know why it showed up. 
$paper-discover
Sources: arxiv (cs.CL, cs.LG, cs.AI), X list "ml-research", subscribed newsletters, RSS.
For each new candidate since the last run:
  - normalize to {title, authors, url, source, date, abstract, surfaced_by}
  - dedup against research/seen.json (match on arxiv id / normalized title)
  - score relevance 0-1 against my themes in research/themes.md
  - keep score >= 0.6; append to research/discovery-queue.jsonl with a 1-line "why"
Update research/seen.json. Report a top-5 digest; archive the rest into the queue silently.

Loop W8 — Paper reading & summarization

Cadence: daily (drains the queue) or on-new-item. Tier: 1→2. Connectors: arXiv (PDF/HTML fetch), the discovery queue, the vault. Memory: per-paper note research/papers/<id>.md + the idea index research/idea-index.md.

For each unread item in the queue, W8 fetches the paper, writes a structured summary, extracts the core concepts, and — the valuable part — harvests follow-up ideas and candidate experiments into a running ledger. A summarizer sub-agent drafts; a checker sub-agent verifies the summary against the actual paper so claimed numbers and methods are not hallucinated. The living artifact is exactly what you asked for: an index of ideas plus paper summaries, cross-linked.

Per-paper summary template

  • Problem & motivation — what gap it addresses, in one or two sentences.
  • Method — the key idea, stripped of notation.
  • Results — headline numbers, datasets/benchmarks, and the baseline they beat.
  • Limitations & caveats — what the authors (or you) think is shaky.
  • Relevance to us — how it touches Nemotron post-training, RM, data, or evals.
  • Follow-ups — ideas and experiments this sparks → appended to the idea index with tags + a backlink to the paper.
Living artifact: idea-index.md is an append-only, tagged ledger of ideas, each row linking back to the paper(s) that inspired it: {idea, tags, source_papers, novelty_guess, status}. Over months this becomes a searchable map of “things worth trying,” not a graveyard of unread PDFs. 
$paper-read
For each unread item in research/discovery-queue.jsonl:
  - fetch the paper; write research/papers/<id>.md using the summary template
  - extract main concepts and any reported numbers
  - CHECKER pass: verify every claimed result/number exists in the source; flag mismatches
  - append follow-up ideas/experiments to research/idea-index.md
    as {idea, tags, source_papers, novelty_guess, status: "new"}
  - mark the item read
Escalate to me only papers scored "high relevance + high novelty".

Loop W9 — Experiment generation

Cadence: weekly or on-demand. Tier: 1→2 — propose only. This loop drafts experiment specs; it never launches training or eval jobs. Spending compute is irreversible and expensive, so a human always selects what runs (then hands it to W2). Keep Tier 3 off here, permanently.

W9 turns the idea index into concrete, testable bets. It clusters related ideas, and for the most promising it drafts a full experiment spec; a critic sub-agent scores each for feasibility, novelty, and cost, and rejects anything vague or infeasible. The output is a ranked backlog you skim and green-light — the loop does the spec-writing toil; you keep the call on what is worth the GPUs.

What a generated experiment spec contains

  • Hypothesis — the specific, falsifiable claim being tested.
  • Change — what to vary (recipe, data blend, reward, method) vs. the baseline.
  • Setup — base model/checkpoint, dataset, eval suite, and the metric that decides success.
  • Success criterion — a verifiable bar (e.g. “+1.5% on suite X without regressing Y”).
  • Smallest first step — the cheapest run that would confirm or kill the idea.
  • Cost & risk — rough compute estimate and what could make it a dead end.
Living artifact: research/experiment-backlog.md — a ranked list of ready-to-run specs, each linked to the ideas (W8) and papers (W7) that motivated it. Approved specs flow into the training-run babysitter (W2) and eval-triage (W1) loops, closing the loop from literature to result. 
$experiment-gen
Read research/idea-index.md (status: new|promising).
Cluster related ideas; for the top clusters draft an experiment spec:
  hypothesis, change-vs-baseline, setup (model/data/eval/metric),
  success criterion, smallest-first-step, rough compute + risk.
CRITIC pass: score feasibility/novelty/cost 0-1; drop specs that are vague or infeasible.
Append survivors to research/experiment-backlog.md, ranked.
Propose only. Do NOT launch any job. Surface the top 3 for my approval.
Why these compound: W1–W3 share a memory of what regressed and why; W7→W8→W9 turn the literature into a ranked experiment backlog that feeds W2/W1; W5 turns all of it into evidence; W6 keeps the code flowing. Together they are an always-on research-operations layer that hands you decisions — what to test, what regressed, what to ship — instead of chores.

Personal Loops — Investing & a Sample-Portfolio Lab

Not financial advice. This is a research and learning harness. Everything here is paper trading by default. The loop’s job is to make you a better-informed operator of your real portfolio, never to trade it autonomously. Keep Tier 3 (live execution) off.

Investing is an almost perfect loop domain: clear cadence (markets close daily), machine-readable signals (prices, fundamentals), a naturally verifiable stop condition (did the ledger reconcile?), and an obvious external memory (a portfolio ledger file). The design goal is a sample-portfolio lab: several model portfolios, each running a different strategy, tracked daily against a benchmark, so over months you accumulate real evidence about which approach fits you before you move a single real dollar.

The lab architecture

Memory: the ledger One file per model portfolio (portfolios/value.jsonl, growth.jsonl, dividend.jsonl…) holding positions, cash, and a dated row of every valuation and trade. The spine of the whole lab.
Connectors: market data A price/fundamentals source (an API or a fetch step). Read-only. The loop never connects to a brokerage execution endpoint.
Skill: the strategy + risk rules Each portfolio gets a SKILL.md: universe, sizing rules, rebalance triggers, hard risk limits (max position %, sector caps, drawdown stop). This is where your intent lives.
Sub-agents: analyst vs. risk officer One sub-agent proposes trades from the strategy; a separate risk-officer sub-agent rejects anything that breaks the risk limits before it is written to the ledger.

Loop P1 — Daily mark-to-market

Cadence: daily after close. Tier: 1.

Fetch closing prices, value every model portfolio, append a dated NAV row to each ledger, and compute return vs. the benchmark (e.g. SPX). Pure observation — it just keeps the books current and never decides anything. 

$portfolio-mark
For each ledger in portfolios/*.jsonl:
  - fetch close prices for all held tickers
  - compute portfolio NAV, daily return, return vs. SPX since inception
  - append: {date, nav, day_return, vs_benchmark, drawdown}
  - flag any position breaching a risk limit in the strategy SKILL
Write nothing to a brokerage. Report flags into the weekly note.

Loop P2 — Weekly rebalance proposal

Cadence: weekly. Tier: 2 (propose only).

The analyst sub-agent reads each strategy’s rules and the week’s data and proposes rebalances; the risk-officer sub-agent vets every proposed trade against the hard limits. Approved-by-risk proposals are written to a weekly review note for your sign-off. Only after you approve does the trade get written to the paper ledger.

Loop P3 — Strategy scoreboard & thesis journal

Cadence: monthly. Tier: 1.

Produces a one-page scoreboard: each model portfolio’s return, volatility, max drawdown, and Sharpe vs. benchmark, plus a short written note on why each is ahead or behind. Over a few months this is the evidence base for deciding which strategy (if any) earns real capital. This is the “maker writes, checker grades” idea applied to your own decisions: the loop reports the numbers; you supply the judgment.

Guardrails specific to money: hard-code risk limits in the skill, not the prompt; keep execution manual; log every assumption (data source, fees, slippage) so the paper results are not lying to you; and re-read the thesis journal monthly to fight cognitive surrender. The danger here is not a bug — it is trusting a smooth report you never checked.

The same machinery that runs eval triage runs your life admin. Your Obsidian vault is already the ideal memory layer — it lives on disk, outside any single conversation, exactly as the spine should. These loops turn scattered tools into one calm morning briefing and a tidy weekly review.

Cadence: before each meeting + after. Tier: 1→2.

Before: pulls attendee context, recent threads, and the relevant doc into a one-page brief. After: reads the transcript, extracts decisions and action items, and drops tasks into the vault with owners. At Tier 2 it drafts the follow-up message for your approval.

Loop L3 — Inbox & commitment triage

Cadence: twice daily. Tier: 2.

Classifies inbound (action / reply / FYI / archive), drafts replies for the easy ones, and surfaces anything where you made or were promised a commitment so nothing quietly slips.

Loop L4 — Weekly review & knowledge gardener

Cadence: weekly. Tier: 1.

Consolidates the week’s daily notes into a review (what got done, what stalled, what is next), links new notes into existing topics, and flags stale tasks. Keeps the vault a living second brain instead of a junk drawer.

Loop L5 — Learning & spaced repetition

Cadence: a few times a week. Tier: 1.

Turns the arXiv digest (W4) and meeting learnings into short review prompts, resurfacing them on a spacing schedule so the things you decided to learn actually stick.

Loop L6 — Habit coach & streak keeper

Cadence: nightly + weekly. Tier: 1. Memory: life/journal.md in the vault.

Asks three short questions about your day, remembers the answers, and once a week tells you what actually changed — mood, energy, recurring blockers, what you keep saying you’ll do. Because the memory persists, it becomes a check-in companion that notices patterns you wouldn’t, instead of a blank page you abandon.

Loop L8 — Nutrition & health log

Cadence: on-event (you send a photo) + weekly. Tier: 1. Memory: life/nutrition.jsonl.

Snap a photo of your plate; it estimates calories/macros and logs them — no separate app, no manual entry. Weekly it summarizes trends against your target and flags drift. The estimate is a draft, not a lab result, so treat it as a directional signal you can correct.

Loop L9 — Deal & price watcher

Cadence: daily. Tier: 2 (alert / propose — never auto-buy). Connectors: price sources, mail. Memory: life/watchlist.md.

Watches the things you’re waiting on — a flight route, a product, a subscription renewal — and pings you the moment the price hits your number, with a one-tap path to act. Anatoli’s example auto-buys; this guide keeps the purchase human-confirmed, because spending money is exactly the kind of irreversible action a loop should propose, not execute.

A no-clickbait briefing on the topics you actually care about — headlines distilled to what happened and why it matters, deduped against what you already saw. The non-work cousin of the W7 paper-discovery loop: same fan-out-and-filter shape, pointed at the rest of your life.

L4Operating systemWork + money + life loops run daily; you mostly review and decide.Let a meta-loop triage which loops to run.
L5Self-evolvingLoops propose changes to their own skills and workflows (dynamic workflows).Hold the line: keep verification and judgment human.
Where the frontier is going: Bishoyi’s self-evolving autoresearch loops (evo) are L5 — a concurrent meta loop rewrites the running loop’s harness because coordination is now code, not context. Worth watching, but note that even there the meta agent is read-only and hands kills/alerts to gated enforcers and humans: the judgment layer does not move. Climb deliberately; do not skip to L5 because it sounds impressive.

Monitoring the Loops — A Single Pane of Glass?

Once you reach L3–L4 you are not running one loop, you are running a dozen across three tools. The obvious operational question follows: how do you see them all at once — what ran, what it cost, what it found, what is stuck, and how the loops feed each other? The short answer in mid-2026: each tool monitors its own loops reasonably well, but no product gives you a unified, cross-tool view — and none of them visualizes how loops interact. That gap is the proposal at the end of this section.

The community has already shown the appetite. Tools like claude-monitor, CAM (“mission control”), and Claude-Code-Agent-Monitor build live dashboards by reading the artifacts agents leave on disk. One of them (fakirAyoub/claude-monitor) already reads both ~/.claude/ and ~/.codex/ — a hint that a unified view is feasible.

The gap: per-tool inboxes, no system view

Two things are missing, and the second is the important one:

  • No cross-tool single pane. Your eval-triage loop might run in Cursor, your paper pipeline in Codex, your code-review loop in Claude Code. There is no one screen that shows all of them with status, last run, cost, and findings.
  • No view of how loops interact. Every existing surface is a flat list of runs. None of them shows that W7 → W8 → W9 → W2 form a chain, that they share idea-index.md, or that a stalled discovery loop is starving the experiment-generation loop downstream. The interactions are invisible.
The key insight that makes a unified dashboard buildable: in this guide’s design, loops interact through shared state files — the memory spine. discovery-queue.jsonl, idea-index.md, experiment-backlog.md, evals/triage-log.md, the portfolio ledgers, the vault’s daily notes. Those files are the edges of the loop graph. If a dashboard knows which loop reads and writes which artifact, it can reconstruct the entire interaction graph for free.

Proposal: a Loop Control Plane

Since the products will not give us a cross-tool, interaction-aware view, we should build one. Working name: Loop Control Plane (CLI loopctl, a local web dashboard). It is read-only observability over the loops you already run — it does not execute anything, so it has zero blast radius. It works by harvesting the same on-disk artifacts the community monitors use, plus a tiny registry that declares each loop’s inputs and outputs.

Data sources to harvest

Codex Automations DB + ~/.codex/ session logs → automation list, run status, findings, tokens.
Claude Code ~/.claude/ JSONL transcripts, tasks/, and hook events → sessions, subagent trees, cost.
Cursor Cloud Agents dashboard/API + local run logs → active agents, schedules, PR artifacts.
Shared memory (the edges) The state files in the vault/repo — queues, ledgers, indices, triage logs — with their last-write timestamps.

No hand-maintained registry — derive it from the automations

You should not hand-maintain a list of your loops. That would just be a second source of truth that drifts the moment you add, rename, or delete an automation. Every tool already stores each automation’s definition — prompt, schedule, type, model, locus — so the control plane should discover the loops by reading those stores, and infer the read/write edges by observing what each run actually touches. The registry is a derived view, regenerated on every harvest, never authored.

Discover the nodes automatically Read each tool’s own automation store: Codex’s automations DB / ~/.codex/, Cursor’s Cloud Agents API, Claude Code’s scheduled tasks + hooks / ~/.claude/. Each entry already carries id, prompt, cadence, tool, and locus — that is your node list, for free.
Infer the edges automatically Don’t declare reads/writes — observe them. Three signals, strongest first: (1) run instrumentation — Claude Code hooks and Codex/Cursor run logs record the files each run edits; (2) mtime correlation — a write to X inside loop A’s run window, then a read of X in loop B’s, implies A→B; (3) prompt/skill parsing — extract referenced paths from the automation’s own text as a hint.

The result is the same dependency graph (loop B depends on loop A if B reads what A writes) — but produced by the system, so it is always in sync with the automations that actually exist.

The only thing a human might add is an optional thin annotation overlay — a friendlier display name, a manual grouping, a “don’t alert on this one” flag — and even those default to values pulled from the automation’s title. Nothing about the graph requires hand-maintenance; the annotations only decorate it.

Build phases

  1. Read-only fleet board (week 1). Harvest the three tools’ logs + artifact mtimes into one SQLite store; render a static fleet table. No registry yet.
  2. Auto-discovery + interaction graph (week 2). Discover loops from each tool’s automation store; infer edges from observed file reads/writes; render the DAG with status overlays.

Tech sketch: a small Go or Node service with file watchers (fsnotify / chokidar) over ~/.claude/, ~/.codex/, and the vault; SQLite for history; a React dashboard with a force-directed graph for the DAG. This is deliberately the same pattern the community Claude monitors already use — the new parts are the cross-tool harvest and the artifact-inferred interaction graph.
Why it belongs in this guide: a control plane is how you pay down the two debts that scale with the loop — it makes cost visible before the bill, and comprehension visible before the drift. It is the L4 “operating system” rung made literal: you stop chasing per-tool inboxes and start operating your whole loop fleet from one screen, while staying the engineer.

Where Loops Run

A loop is only as reliable as the machine it runs on. Before you trust a loop to work overnight or while you are away, you have to answer one question: where does it actually execute, and what has to stay awake for it to fire? The answer is not uniform — it varies by tool, and getting it wrong is the most common reason a “daily” loop quietly stops running.

The gotcha in one line: most automations run locally by default. A local loop dies when your laptop sleeps, reboots, drops VPN, or closes the app — silently. If a loop must run while you are away, it has to live somewhere that is always on.

The two execution models

Local execution The loop runs on your machine — inside a desktop app or a terminal session. Fast to set up, full access to your local checkout and tools, but it only runs while your machine is awake and the app/session is alive.
Remote / cloud execution The loop runs on a remote VM, a server, or CI. It keeps going with your laptop closed, but needs its environment provisioned (repo, secrets, network) and is a step removed from your local state.

Per-tool: where automations run & what must stay awake

ToolDefault locusLaptop awake?How to run it truly unattended
Codex Local — in the desktop app Yes. App must be open; machine must not sleep. Enable “Prevent sleep while running” for overnight runs. Move it server-side with the Codex SDK or a GitHub Action.
Cursor Cloud — Cloud Agents on remote VMs No. Schedules/events fire in the cloud; you can close the laptop and check cursor.com/agents later. Already remote — nothing extra needed. Provision the environment (repo, secrets, network).
Claude Code Local — terminal session Yes. /loop, cron tasks, and hooks run in your local session and need the machine awake. Push the loop to GitHub Actions or any always-on server / box.
Rule of thumb: if a loop must run overnight or while you are away, either (a) run it as a Cursor Cloud Agent, or (b) host the Codex/Claude loop on a server, GitHub Action, or always-on box. Keeping the laptop awake works for short windows but is the fragile option — it dies on sleep, reboots, and VPN drops.

The always-on Linux VM: your own loop host

You already have the best home for unattended loops: an always-on Linux VM. It is the server locus in its purest form — never sleeps, no GUI app to keep open, no dependence on a vendor’s cloud or on GitHub Actions minutes. Treat it as your private, persistent loop host: the place where every loop that must run “whether or not my laptop is open” actually lives. It is also the natural home for the Loop Control Plane itself, which wants to be an always-on service watching artifacts and harvesting run logs.

What to run on it

Headless agent loops Run the Codex CLI/SDK and Claude Code headless on the VM — not the desktop GUI apps. Schedule them with cron or, better, systemd timers (restart-on-failure, journald logs, dependency ordering). This is how W1, W2, W7–W9, and P1–P3 get a reliable cadence.
The control plane Host loopctl + its dashboard here as a long-lived service. The VM watches ~/.claude/, ~/.codex/, and the synced repo/vault, stores history in SQLite, and serves the fleet board / interaction graph on a port you reach over the network.
Shared memory, in one place Keep the loops’ state files (queues, idea-index.md, ledgers, triage logs) on the VM and sync the Obsidian vault via git. Loops read/write the canonical copy on the VM; your laptop pulls when you want to review. One source of truth, always reachable.
Event triggers & webhooks Because it is always reachable, the VM can host webhook endpoints — a new CL, a Slack event, a finished training job can trigger a loop instead of waiting for the next cron tick.

How to set it up

  1. Provision auth once. Install nv-tools and run its auth flow on the VM, plus any agent API keys and git credentials. The VM has no access to your laptop’s tokens, so it needs its own.
  2. Sync the repo/vault. Clone the repo and the Obsidian vault on the VM; set a git pull --rebase + push cadence (or a systemd path unit) so memory stays consistent across machines.
  3. Schedule the loops. One systemd timer (or cron line) per loop, each invoking the headless agent with the loop’s prompt/skill. Send stdout/stderr to journald so the control plane can harvest it.
  4. Run the control plane. Start loopctl as a systemd service; point it at ~/.claude/, ~/.codex/, and the synced repo so it auto-discovers the loops running right there.
# /etc/systemd/system/loop-w7-discovery.timer
[Timer]
OnCalendar=*-*-* 07:00:00
Persistent=true          # catch up if the VM was down at trigger time

# /etc/systemd/system/loop-w7-discovery.service
[Service]
WorkingDirectory=/home/me/obsidian
ExecStart=/usr/local/bin/codex exec --skill paper-discover
# journald captures output -> loopctl harvests it for the fleet board
Caveats to plan for: the VM has no GUI, so Codex/Claude desktop automations don’t apply — use the CLI/SDK paths instead. It has no uncommitted local state, so anything depending on your working tree must be committed/synced first. And it needs its own secrets and network reach (VPN/proxy to internal services); provision them once and keep them off the repo. Keep destructive/irreversible actions human-confirmed even here — an always-on host makes a runaway loop run all night, not just until you close the laptop.
Net effect: the always-on VM turns “loops that run when I happen to be online” into a genuine 24/7 loop fleet, with one canonical memory and one dashboard — and it does it on hardware you control, without renting cloud agents or burning CI minutes.

Choosing a locus per loop

Match the home to the job. The right question is not “which tool is best” but “what does this loop need?”

Keep it local when… The loop is interactive or you are iterating on it; it needs your uncommitted local state; it runs only while you are at the keyboard anyway (e.g. a meeting-prep loop during work hours); or it touches private data you do not want on a remote VM.
Go remote/cloud when… It must run overnight or on a fixed cadence regardless of you; it is long-running (training babysitter, multi-hour agent); it should survive sleep/reboots; or it is triggered by external events (a new CL, a webhook) that arrive when you are away.
Map it to the loops in this guide. The morning briefing (L1) and meeting prep (L2) are fine local — you are around when they matter. But the nightly eval-triage (W1), the training-run babysitter (W2), the daily paper-discovery pipeline (W7–W9), and the daily mark-to-market (P1) all belong on the always-on Linux VM so they fire whether or not your laptop is open. A loop that only runs “when I happen to be online” is not really a loop.

Surface the execution locus (also auto-derived)

Because the locus determines reliability, it should be a first-class field in the control plane — and like everything else, it is discovered, not declared. The tool already knows where each automation runs: a Cursor Cloud Agent is cloud, a Codex desktop automation is local-app, a Claude /loop is local-terminal, a loop wired into CI is github-action. The harvester reads that from each automation’s definition and tags the node automatically, so the fleet board can flag which loops silently stop when your laptop sleeps — without you maintaining a thing. 

# DERIVED locus per loop — read from each tool's automation definition.
W1-eval-triage      tool=cursor       locus=cloud           # runs regardless of my laptop
L1-morning-briefing tool=claude-code  locus=local-terminal  # fine — I'm around when it matters
W7-paper-discovery  tool=codex        locus=github-action   # moved off the laptop for reliability

Bottom line: decide each loop’s home on purpose. Local is the easy default and the right call for things you babysit anyway; cloud/CI is the home for anything that has to run without you. The failure you are designing against is the silent one — a loop you think is running every night that actually stopped the first time your laptop went to sleep.

Your First Week — A Concrete Rollout

Do not boil the ocean. Build one loop end-to-end, feel the shape, then replicate. A realistic week:

Day 1 — Pick & map Choose the single chore that annoys you most (suggest: W5 standup synthesizer or L1 morning briefing). Fill in the Loop Design Canvas for it.
Day 2 — Write the skill Capture the conventions, formats, and “don’t do X” rules in a SKILL.md. Boring, specific description.
Day 3 — Wire the memory Create the markdown/JSONL state file in the vault. Make the loop read it at start and append at end.
Day 4 — Schedule it (Tier 1) Turn it into an automation on a daily cadence, read-only, reporting into an inbox/daily note.
Day 5 — Add the verifier Add a checker sub-agent or a verifiable stop condition. Confirm it catches a deliberately bad run.
Day 6–7 — Observe & tune Let it run. Read every output. Tune the skill where it guessed wrong. Decide if it has earned Tier 2.
The bar for “it worked”: after one week you should be reviewing the loop’s output instead of doing the chore, and you should trust its “nothing to report” as much as its findings. That trust — earned, not assumed — is the whole game.

Guardrails & When NOT to Loop

Loops are leverage, and leverage cuts both ways. A few hard rules keep them an asset.

Don’t loop the irreversible Anything destructive or hard to undo (sending external mail, spending real money, deleting, force-pushing) stays human-confirmed. Keep it at Tier 2 forever.
Don’t loop the one-off If it does not genuinely recur, a loop is overhead. Just run the agent once.
Don’t loop what you can’t verify No verifiable stop condition means no unattended run. Escalate to a human instead of declaring done.
Cap the blast radius Scope tokens, frequency, file paths, and write permissions per loop. A runaway loop should be annoying, not catastrophic.
Read on a cadence Schedule yourself to actually read what your loops produced — that is how you pay down comprehension debt before it compounds.
Keep an opinion The moment you are taking outputs without a view, you have surrendered. Designing the loop is the cure only if you stay the engineer.

Osmani’s closing is the right note to end on: build the loop, but build it like someone who intends to stay the engineer, not just the person who presses go. Set up your loops — and remember that prompting your agents directly is still effective. It is about balance, and the loop will only ever be as good as the judgment you keep in the room.
